# Grouped Twin Search: что изменилось

`POST /private/twin/search/grouped/v1`

Сначала выполняется плоский поиск твинов ровно одного класса. Затем те же твины раскладываются в дерево. Другие твины поиск не добавляет.

## Запрос

`levels` — от 1 до 3 элементов, сверху вниз. Больше трёх не доходит до выборки: HTTP 400, код `13701` (`VALIDATION_DTO_FAILED`).

Элемент уровня — только поле:

```json
{ "fieldId": "<twin class field id>", "sort": "NAME_ASC" }
```

`type`, `linkId` и `nodeEnd` в запросе нет. Отдельного элемента `LINK` нет.

`search` обязателен. `search.twinClassIdList` обязан содержать ровно один класс. Пустой список и два класса — 400, выборка не начинается. Динамическое поле чужого класса тоже 400. Поле родителя проходит только если `inheritable = true` либо оно объявлено на самом искомом классе. Базовые системные поля этой проверке не подвергаются. Некорректный `memberSorts` отклоняется до подсчёта фильтра.

Перед выборкой считается число твинов фильтра. Больше 5000 — 400, код `TWIN_SEARCH_INCORRECT`, `findAll` не вызывается. Ноль совпадений — пустое дерево без `findAll`.

`memberSorts` — до двух базовых полей. Пустой список сортирует листья по `createdAt DESC`, затем `id ASC`.

## Ответ

Дерево глубиной в число уровней. На верхних уровнях — `groups`. На последнем — `twinIdList`, не полные твины.

Полный `TwinDTOv2` лежит в `relatedObjects.twinMap` и только если в запросе задан `showTwinMode`. Одна задача, попавшая в несколько узлов, сериализуется там один раз. Без `showTwinMode` в ответе структура и id. Голова и твин поля-ссылки, которые пользователь не может читать, в `twinMap` не попадают; id в ключе остаётся. Имена для сортировки `NAME_*` по твину читаются с той же проверкой. Имена пользователей по-прежнему без неё. Статус, класс, flavor и data list берутся из своих show-режимов запроса (`showTwin2StatusMode`, `showTwin2TwinClassMode`, `showTwinFlavor2DataListOptionMode`, `showTwinField2DataListOptionMode`). Без режима словарь не заполняется.

Ключ узла — вложенный объект, не набор разных полей на группе:

```json
{ "type": "USER", "value": "<id или скаляр>" }
```

Пустая группа сохраняет `type` и пишет `"value": null`.

| `type` | Откуда значение | Словарь related objects |
| --- | --- | --- |
| `USER` | assignee, owner, creator | `userMap` |
| `STATUS` | статус | `statusMap` |
| `TWIN_CLASS` | класс | `twinClassMap` |
| `TWIN` | голова или поле типа Linked twin | `twinMap` |
| `DATA_LIST_OPTION` | flavor и data list, в том числе `TASK.workType` | `dataListsOptionMap` |
| `TEXT`, `DECIMAL`, `BOOLEAN`, `TIMESTAMP` | simple, decimal, boolean, timestamp | словаря нет, `value` и есть значение |

У `DECIMAL` хвостовые нули снимаются, поэтому `0` и `0.00` попадают в одну группу. В ключе ответа `linkId` нет: для поля-ссылки достаточно `type: TWIN` и id дальнего твина.

`count` узла — число разных листьев в поддереве. Если первый уровень кладёт лист в несколько узлов (multiple select или поле-ссылка с несколькими связями), сумма `count` корней больше числа твинов фильтра. Для статуса и assignee сумма корней совпадает с выборкой.

## Поле-ссылка

Группировка по связи идёт через поле класса типа Linked twin (`FieldTyperLink`, id 1310), а не через id связи в запросе. У поля в параметрах уже записан `linkId`. Ключ — твин на дальнем конце прямой связи (`dst`). Направление определяется классом поля. Несколько связей кладут задачу в несколько узлов. Нет связи — группа с `"value": null` и `type: TWIN`.

Обратное link-поле (лист — `dst`) группированный поиск не принимает: 400 `TWIN_SEARCH_CONFIG_INCORRECT`. Общая загрузка входящих связей по-прежнему выключена. `/private/twin/count/v1` такое поле по-прежнему считает в SQL.

`TwinFieldStorageLink.countGroup` больше не возвращает `null`.

Связь, для которой на классе нет такого поля, сгруппировать нельзя.

## Сортировка

У каждого уровня свой `sort`. По умолчанию `NAME_ASC` для пользователя, головы и поля-ссылки, `KEY_ASC` для остальных. `NAME_*` для статуса, класса, flavor и data list — 400: имя лежит в i18n. `KEY_*` сравнивает само значение, не только UUID. При `NAME_*` и `KEY_*` пустой ключ последний. При `COUNT_*` группы идут по размеру, пустой ключ уходит в конец только при равном `count`.
