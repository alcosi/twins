# Grouped Twin Search — результаты проверки

Дата: 2026-11-11. Локальный сервер `http://127.0.0.1:8080` (профиль `devlocal`), база `wnr`.

Заголовки каждого запроса: `DomainId: f67ad556-dd27-4871-9a00-16fb0e8a4102`, `AuthToken: 608c6d7d-99c8-4d87-89c6-2f72d0f5d673,9a3f6075-f175-41cd-a804-934201ec969c`, `Channel: WEB`.

Эндпоинт: `POST /private/twin/search/grouped/v1`.

Операционный класс `TASK`: `7c027b60-0f6c-445c-9889-8ee3855d2c59`, 855 видимых задач. Эталоном была текущая база, не снимок из постановки. Протокол прогона: `checks.json`. Пример пустой группы: `raw/s2-null-assignee-group.json`.

Поля близнеца в листе появляются только с `showTwinMode=DETAILED`. Без параметра резолвер подставляет первое значение `TwinMode`, это `HIDE`, и элемент `twins` сериализуется как `{}`. `SHORT` отдаёт id и имя. Для сверки класса, исполнителя, статуса, головы и `createdAt` нужен `DETAILED`. Связанные объекты попадают в `relatedObjects` при `lazyRelation=false` и своём show-режиме: пользователи — `showTwin2UserMode`, статусы — `showTwin2StatusMode`, классы — `showTwin2TwinClassMode`, головы — тот же `showTwinMode`. Опция списка для динамического поля требует сразу два параметра, см. замечание ниже.

## Итог

Сценарии S1–S9 и S12 на колонках `twin` и на `TASK.workType` выполняются. Группа без ключа сериализуется как `null` и стоит последней при сортировке по имени и по ключу. `count` равен числу листьев. Сумма по группам для однозначного поля равна 855. Фильтр убирает пустые группы. Чужой домен не даёт 403. Негруппируемые поля отвечают 400, `TWIN_SEARCH_CONFIG_INCORRECT` (11604), до выборки.

Два дефекта ответа. Десятичное поле режет численно равные значения по масштабу, и после разбора JSON это несколько групп с одним и тем же ключом `0`. Ключ timestamp сдвигается на часовой пояс JVM.

В `checks.json` пять строк помечены как непройденные. Три из них — неверный оракул или более строгая проверка, чем текст постановки: порядок листьев по имени совпал с `ORDER BY name, id` в `en_US.utf8`; опции списка появляются при нужном show-режиме; неизвестный id поля — это 404, а не 11604. Реальные расхождения — decimal и timestamp.

## Дефекты

### 1. Decimal: один ноль становится тремя группами

Поле `TASK.progress` (`e454db8e-c8d8-48cb-9684-00abef38ee9e`). В `twin_field_decimal` ноль лежит в трёх масштабах: `0` (40 задач), `0.0` (123), `0.00` (668). Ещё одна строка `0.00` висит на твине не этого класса и в выборку не входит.

`POST` с `groupSort=KEY_ASC` вернул 200 и 20 групп. Размеры совпали с этими строками, сумма `count` равна 855. В сыром JSON три ключа записаны как `0`, `0.0` и `0.00`. После обычного разбора JSON все три числа равны `0`, поэтому клиент видит три группы с одним ключом и счётчиками 668, 123 и 40.

В PostgreSQL `numeric` считает эти значения равными, и `GROUP BY` счётчика слил бы их в одну группу. Группирующий поиск кладёт `BigDecimal` в ключ карты: `equals` учитывает масштаб, `compareTo` — нет. Равные по величине нули не сливаются и между собой не упорядочиваются.

То же видно на ненулевых масштабах, просто без столкновения: `0.10` уходит клиенту как `0.1`, `1.00` как `1`, `22.00` как `22`.

### 2. Timestamp: ключ сдвинут на пояс JVM

Поле `OBJECT_EXT.startDate` (`ae6118ef-f588-3b8b-a87a-5d061e12378e`), класс `b00b43a8-c1ab-3555-9c99-3442e004432f`, одна запись. В базе `2026-01-01 00:00:00`. В `groupedFieldValues` пришло `"2025-12-31T21:00:00.000Z"` — те же сутки по UTC+3, но уже предыдущий календарный день в UTC.

Запрос при этом 200, группа одна, `count = 1`. Поле принимается и не получает «is not countable». Сдвигается значение ключа.

Текстовое поле того же класса (`9e24f738-0a77-325e-af96-c85eb3ef1e35`) вернуло ключ `"Object Name"`, как в `twin_field_simple`. `NAME_ASC` и для timestamp, и для текста — 400, 11604, `NAME sort is not supported`, и эта проверка срабатывает раньше потолка в 5000.

Листья внутри группы идут по `created_at DESC`, затем `id ASC`. Пустой `memberSorts` совпал с явным `createdAt DESC`.

Самая большая группа — 501 задача. Обычная страница поиска — 10. Повтор того же тела вернул те же группы и тот же порядок листьев. Второй запрос занял 58 с, первый 32 с.

### S10. Размер групп и имя листа

`COUNT_DESC`: первая группа — 501, вторая — пустой исполнитель на 87. Пустой ключ последним не ставится, он стоит по размеру. При равном размере тай-брейк — сырой ключ, пустой ключ в этой паре последний. Это совпадает с абзацем постановки про `COUNT_*` и расходится с более поздним замечанием, где пустой ключ последний при любой сортировке.

Листья при `memberSorts` по имени идут как `ORDER BY name ASC, id ASC` в коллации базы `en_US.utf8`, не как сравнение кодов Unicode. У исполнителя `c17886e7-4867-451a-bd00-c97626ec89c1` первым пришёл `3794ea84-3a89-44bb-bd2c-d45c5841c0f2` («32 Благоустройство»), а не задача, чьё имя начинается с кавычек. В группе без исполнителя на позиции 11 — `01a0ce15-7f57-71ce-9d90-4c961393b2c3` («123234»), как в том же `ORDER BY`. Порядок групп по имени считается уже в Java через `String.compareTo`.

### S11. Тип работ

`workType` `95f2c8ca-8b79-4971-9726-270a11c7d031`, в параметрах поля `multiple=false`. 16 групп, сумма `count` равна 855, пустой группы нет: строки поля есть у всех задач. Состав и размеры совпали с `twin_field_data_list` (крупнейшая опция `d4447cdc-d235-49a6-b6ef-569622855650`, 783). Порядок ключей — сравнение UUID, как у `KEY_ASC`, хотя `groupSort` в запросе не передавался.

Опции в `relatedObjects.dataListsOptionMap` есть, если передать и `showDataListOptionMode=SHORT`, и `showTwinField2DataListOptionMode=SHORT`. Первого параметра недостаточно: загрузчик группы открывается, а `postpone` смотрит уже на pointer-режим, который по умолчанию `HIDE`, и опция в ответ не кладётся. Имя опции на проверке одной задачи — «Other work types». `NAME_ASC` — 400.

Boolean `reportRequired`: группы `false` (758), `true` (54), `null` (43). Пустое значение в карте сохранилось: `"groupedFieldValues": { "<field>": null }`. Сумма 855.

Multiple select в домене нет (`field_typer_params.multiple = true` — 0 полей). Ветку «твин входит в каждую выбранную опцию» прогнать не на чем.

### S12. Второй уровень

Тело с дополнительным `groupFieldIds: [assignee, status]` принято как обычный запрос по `groupFieldId`. HTTP 200, группы плоские, вложенного `groups` нет. Отдельной ошибки «вложенность в v1 не поддерживается» нет: лишнее поле Джексон отбрасывает.

## Потолок ответа

Пустой `search` и группировка по исполнителю: HTTP 400, код 11606, `grouped search matches 11668 twins, limit is 5000`. Урезанного дерева нет.

В постановке архитектора потолка нет. В коде предел 5000, и он совпадает с замечанием к постановке. На 855 задачах класса предел не мешает. Запрос класса с `DETAILED` занимает примерно 30–45 с.

## Что не проверялось

Скрытый твин внутри домена при том, что соседние задачи того же класса видны. Число SQL и план индекса. Пагинация групп: её в контракте нет, и query-параметры страницы на ответ не влияют.
