# Grouped Twin Search: плоский поиск одного класса, дерево глубины 3

Статус: архитектурная постановка для текущей ветки, приведена к реализованному контракту. Домен-пример `wnr` ниже только иллюстрация, идентификаторы в код не переносятся. Дельта против предыдущей редакции — в `grouped-twin-search-changes.md`.

## Задача

Сначала выполняется плоский поиск твинов одного класса. Затем эти же твины раскладываются в дерево глубиной до 3. Каждый уровень — группировка по полю. Листья — твины плоского поиска, других твинов поиск не добавляет.

Порядок уровней задаёт клиент. Пример, не фиксированная схема: первый уровень — статус, второй — assignee, третий — поле-ссылка. На месте статуса может стоять другое поле, поле-ссылка может стоять на любом из трёх уровней.

Узел поля — значение этого поля у листа. Для статуса это статус, для assignee — пользователь, для data list — опция. Узел поля-ссылки — твин на дальнем конце связи (`dst`). Сам связанный твин в плоский поиск не входил и листом не становится.

Задача без исполнителя, без значения поля или без строки связи остаётся в группе с пустым ключом на соответствующем уровне. Так в дереве сохраняются все твины плоского поиска.

`POST /private/twin/search/v4` возвращает ту же выборку постранично. Этот endpoint возвращает её целиком, уже разложенной. Пагинации нет, но есть потолок: больше 5000 совпадений — 400, `TWIN_SEARCH_INCORRECT`, выборка не выполняется.

## Глубина

В запросе от 1 до 3 критериев, сверху вниз. Глубина ответа равна длине списка. Три уровня — обязательная возможность. Один и два уровня собираются тем же алгоритмом: последний критерий несёт листья, верхние несут вложенные группы.

Все критерии читают ключ с листа, то есть с твина плоского поиска. Статус, assignee и поле-ссылка из примера — свойства одной и той же задачи. Следующий уровень не переключается на твин-узел предыдущего уровня и не идёт к голове головы.

Голова отдельным типом критерия не задаётся. Группировка по голове — это поле `head` (`twin.head_twin_id`): узел — твин-голова листа. Цепочка из нескольких голов в эту задачу не входит.

Одинаковый `fieldId` дважды — 400. Два поля-ссылки допустимы, если это разные поля (у них разные `linkId` или разный класс поля).

Длина списка 0 или больше 3 — 400, выборка не начинается.

## Как режется один лист

Поле с одним значением кладёт лист в один узел. Колонки `twin` такие. Динамическое поле с несколькими строками (data list) и поле-ссылка с несколькими строками кладут лист в несколько узлов этого уровня.

`count` узла — число различных листьев в его поддереве. Задача с двумя связями одного поля-ссылки даёт два узла на этом уровне и единицу в `count` статуса и assignee. Сумма `count` детей может быть больше `count` родителя. Сумма `count` корней равна числу твинов плоского поиска: пустые ключи не выкидывают лист.

## Поле

Критерий — только `fieldId` и `sort`. Отдельного критерия `LINK` нет: группировка по связи идёт через поле класса типа Linked twin (`FieldTyperLink`, featurer 1310).

Базовое поле законно, когда `TwinSearchServiceV2.convertToEntityField` возвращает колонку. Динамическое законно, когда оно принадлежит искомому классу (`TwinClassFieldService.isValidForClass`: свой класс либо родительский с `inheritable = true`) и его `TwinFieldStorage.countGroup` возвращает выражение. Нарушение — 400, `TWIN_SEARCH_CONFIG_INCORRECT`.

| Поле | Колонка | Узел |
| --- | --- | --- |
| assignee `00000000-0000-0000-0011-000000000007` | `twin.assigner_user_id` | пользователь |
| owner `00000000-0000-0000-0011-000000000006` | `twin.owner_user_id` | пользователь |
| creator | `twin.created_by_user_id` | пользователь |
| status | `twin.twin_status_id` | статус |
| class | `twin.twin_class_id` | класс |
| head | `twin.head_twin_id` | твин-голова |
| flavor | `twin.flavor_data_list_option_id` | опция списка |

Остальные UUID берутся из `SystemIds.TwinClassField.Base`.

Динамические хранилища с `countGroup`: data list (multiple select помечает `isDistinctGroup`), simple, decimal, boolean, timestamp, link. Поле-исполнитель класса user сюда не входит: исполнитель задачи входит как колонка assignee.

## Поле-ссылка

Группировка по связи идёт через поле класса типа Linked twin: у поля в параметрах записан `linkId`. Ключ — твин на дальнем конце прямой связи (`dst`); направление определяется классом поля через `LinkService.detectLinkDirection`.

- Прямое link-поле (лист — `src`) принимается.
- Обратное link-поле (лист — `dst`) — 400 `TWIN_SEARCH_CONFIG_INCORRECT`: загрузка обратных связей в память в системе отключена.
- Связь, для которой на классе нет поля, сгруппировать нельзя.
- Несколько строк кладут лист в несколько узлов. Ноль строк — пустой ключ.

Связи грузятся одним целевым запросом `srcTwinId IN :leafIds AND linkId IN :resolvedLinkIds`, без загрузки посторонних связей и без гидратации dst-твинов. Строки не фильтруются по праву чтения dst: id нужен только как ключ, тела твинов проходят свою проверку прав в related objects, и `/private/twin/count/v1` считает эти же группы в SQL без фильтра.

## Контракт

`POST /private/twin/search/grouped/v1`

Право: `@ProtectedBy({Permissions.TWIN_MANAGE, Permissions.TWIN_VIEW})`.

Параметров страницы нет.

```json
{
  "search": {
    "twinClassIdList": ["<один класс, например TASK>"]
  },
  "levels": [
    { "fieldId": "<status>", "sort": "KEY_ASC" },
    { "fieldId": "00000000-0000-0000-0011-000000000007", "sort": "NAME_ASC" },
    { "fieldId": "<link-поле класса>", "sort": "NAME_ASC" }
  ],
  "memberSorts": [
    { "twinClassFieldId": "<createdAt>", "direction": "DESC" }
  ]
}
```

`search` — `TwinSearchDTOv1`, обязателен. В нём ровно один id в `twinClassIdList`; пустой список и больше одного класса — 400. Остальные условия плоского поиска сужают выборку до группировки. Сортировки в `search` нет: порядок листьев задаёт `memberSorts`.

`levels` — от 1 до 3 элементов `{fieldId, sort}`.

`sort` уровня:

| Значение | Порядок узлов |
| --- | --- |
| `NAME_ASC` / `NAME_DESC` | Имя ключа. Assignee, owner, creator — `user.name`. Head и поле-ссылки — `twin.name`. Status, class, flavor и data list в этом режиме — 400: имя лежит в i18n |
| `COUNT_DESC` / `COUNT_ASC` | `count` узла; при равенстве — id ключа, пустой ключ последний |
| `KEY_ASC` / `KEY_DESC` | Само значение ключа (UUID, строка, число, boolean, timestamp), не только UUID. Пустой ключ последний |

Для пользовательских полей, головы и поля-ссылки по умолчанию `NAME_ASC`. Для status, class, flavor и data list — `KEY_ASC`.

`memberSorts` — до двух базовых полей, поддержанных `TwinSearchServiceV2.createSortSpecification` (имя, `createdAt`, статус и другие из белого списка; `head` и `id`, например, не сортируемые — 400). Пустой список — `createdAt DESC`, затем `id ASC`. Сортировка листьев не переставляет узлы. Некорректный `memberSorts` отклоняется до подсчёта фильтра.

Ответ на примере выше:

```json
{
  "groups": [
    {
      "key": { "type": "STATUS", "value": "<статус>" },
      "count": 10,
      "groups": [
        {
          "key": { "type": "USER", "value": "<пользователь>" },
          "count": 4,
          "groups": [
            {
              "key": { "type": "TWIN", "value": "<dst>" },
              "count": 2,
              "twinIdList": ["<twin id>", "<twin id>"]
            }
          ]
        }
      ]
    }
  ],
  "relatedObjects": { }
}
```

На последнем уровне лежит `twinIdList` — id листьев в порядке `memberSorts`. На верхних — `groups`. При одном критерии корни сразу содержат `twinIdList`. Полные `TwinDTOv2` попадают в `relatedObjects.twinMap` и только если в запросе задан `showTwinMode`; одна задача, попавшая в несколько узлов, сериализуется один раз.

Ключ узла — вложенный объект `{ "type": ..., "value": ... }`. `type` — `TwinGroupValueType` — выбирает карту related objects:

| `type` | Откуда значение | Словарь related objects |
| --- | --- | --- |
| `USER` | assignee, owner, creator | `userMap` |
| `STATUS` | статус | `statusMap` |
| `TWIN_CLASS` | класс | `twinClassMap` |
| `TWIN` | голова или поле-ссылка | `twinMap` |
| `DATA_LIST_OPTION` | flavor и data list, в том числе `TASK.workType` | `dataListsOptionMap` |
| `TEXT`, `DECIMAL`, `BOOLEAN`, `TIMESTAMP` | simple, decimal, boolean, timestamp | словаря нет, `value` и есть значение |

Пустая группа сохраняет `type` и пишет `"value": null` (поле не вырезается из JSON). У `DECIMAL` хвостовые нули снимаются (`stripTrailingZeros`): `0` и `0.00` — одна группа. `TIMESTAMP` отдаётся как `LocalDateTime` без сдвига таймзоны. Статус, класс, flavor и data list берутся из своих show-режимов запроса (`showTwin2StatusMode`, `showTwin2TwinClassMode`, `showTwinFlavor2DataListOptionMode`, `showTwinField2DataListOptionMode`); без режима словарь не заполняется.

Голова и твин поля-ссылки, которые пользователь не может читать, в `twinMap` не попадают; id в ключе остаётся. Имена для сортировки `NAME_*` по твину читаются с той же проверкой. Имена пользователей читаются без неё (`UserService.isEntityReadDenied` сейчас всегда false). Невидимые листья отсекаются фильтром плоского поиска до группировки.

## Как выполняется запрос

Одна read-only транзакция.

1. Валидация до выборки: один класс, длина и уникальность критериев, поле по правилам выше, `memberSorts`.
2. `COUNT` фильтра: 0 — пустое дерево без `findAll`; больше 5000 — 400.
3. Все твины одного класса по фильтру, с сортировкой листьев, без `Pageable`.
4. Пакетная загрузка значений динамических полей из `levels`; связи — один целевой запрос по id листьев и `linkId` полей-ссылок.
5. Сборка дерева в памяти. Ключ каждого уровня считается по листу. Пустое значение — своя группа. Повтор листа на уровне поля-ссылки или multiple select размножает только этот уровень.
6. `count` — размер множества id листьев поддерева.
7. Узлы уровня сортируются своим `sort`, имена для `NAME_*` догружаются одним запросом на уровень.

`GROUP BY` счётчика для ответа не используется: он не возвращает листья. `countGroup` нужен как проверка поля и как контракт `/private/twin/count/v1`.

Индекс. Выборка класса по домену и выборка связей по `(src_twin_id, link_id)`. Миграция — после `EXPLAIN` на объёме `wnr`, если план показывает seq scan. Индекс не ограничивает полноту ответа.

## Сценарии

Операционный `TASK` домена `wnr`: `7c027b60-0f6c-445c-9889-8ee3855d2c59`. Идентификаторы в код не переносятся.

### S1. Статус, assignee, поле-ссылка

Фильтр: один класс `TASK`. Уровни: status `KEY_ASC`, assignee `NAME_ASC`, link-поле `NAME_ASC`. Листья — `createdAt DESC`.

Ожидание:

- корни — статусы задач фильтра, по UUID статуса;
- внутри статуса — исполнители этих задач, по `user.name`;
- внутри исполнителя — `dst` связи link-поля, по `twin.name`;
- листья под узлом — задачи с этим статусом, исполнителем и `dst`;
- задача другого класса отсутствует;
- сумма `count` корней равна числу задач фильтра.

### S2. Пустые ключи

Есть задача без assignee и задача без строки связи link-поля.

Ожидание: под своим статусом есть узел assignee с `"value": null`, последним при `NAME_ASC` и `KEY_ASC`. Под исполнителем есть узел link-поля с `"value": null` и `"type": "TWIN"`. Обе задачи присутствуют. Остальные уровни для них заполнены своими значениями.

### S3. Несколько связей у одной задачи

У задачи два `dst` одного link-поля. Статус и assignee те же.

Ожидание: два узла link-поля, в каждом эта задача один раз. `count` assignee и `count` статуса считают её один раз. Сумма `count` узлов link-поля больше `count` assignee.

### S4. Фильтр до группировки

К S1 добавлено условие плоского поиска, оставляющее один статус.

Ожидание: в корнях один статус. Исполнители и связи посчитаны только по оставшимся задачам.

### S5. Короче трёх уровней

Один уровень assignee. Два уровня: status, затем assignee.

Ожидание: при одном уровне у корня сразу `twinIdList`. При двух `twinIdList` лежит на втором уровне. Набор листьев тот же, что у плоского поиска этого фильтра.

### S6. Четвёртый критерий

В `levels` четыре элемента.

Ожидание: 400, выборка не выполняется.

### S7. Класс

`twinClassIdList` пуст или содержит два id.

Ожидание: 400.

### S8. Негруппируемое поле

В любом из трёх слотов — имя, `createdAt`, динамическое поле с `countGroup = null` или поле чужого класса.

Ожидание: 400, `TWIN_SEARCH_CONFIG_INCORRECT`, до `COUNT` фильтра. Data list, simple, decimal, boolean, timestamp и link-поле своего класса проходят.

### S9. Повтор критерия

Два раза один `fieldId`.

Ожидание: 400. Два разных link-поля на двух уровнях — обычное дерево.

### S10. Невидимая задача

Часть задач фильтра пользователю не видна.

Ожидание: их нет ни на одном уровне и ни в одном `count` — их отсекает фильтр плоского поиска. Узел, под которым не осталось видимых задач, отсутствует. Ответ 200.

### S11. Тип работ как поле

`TASK.workType` (`95f2c8ca-8b79-4971-9726-270a11c7d031`) — data list. Он ставится на любой уровень.

Ожидание: узел — `{"type": "DATA_LIST_OPTION", "value": "<dataListOptionId>"}`, опция в `dataListsOptionMap` при заданном show-режиме. Это не link и не отдельный твин типа работ.

### S12. Сортировки не смешиваются

Корни `COUNT_DESC`, листья по имени.

Ожидание: первым идёт статус с наибольшим числом различных задач. Внутри уровня link-поля листья идут по имени.

## Задачи реализации

1. DTO запроса: `search` (`TwinSearchDTOv1`, `@NotNull @Valid`), `levels` (`@Size(min = 1, max = 3)`), `memberSorts` (`@Size(max = 2)`). Элемент уровня: `fieldId`, `sort`.
2. DTO узла: `key` (`{type: TwinGroupValueType, value}`, `value` не вырезается при null), `count`, `groups`, `twinIdList`. `twinIdList` заполняется только на последнем уровне. Ответ расширяет `ResponseRelatedObjectsDTOv1`. Блока `pagination` нет.
3. Доменные объекты. DTO в сервис не протекают, сущности в JSON не сериализуются.
4. Валидация до выборки: один класс, длина критериев, уникальность `fieldId`, принадлежность полю класса (`isValidForClass`), резолвция link-поля (прямое направление), запрет `NAME_*` для ключей с i18n-именем, `memberSorts` по белому списку базовых полей.
5. `TwinGroupedSearchService.search`, read-only. `COUNT` до `findAll`, потолок 5000. Полная выборка класса без `Pageable`. Поля пакетом через storage; связи одним целевым запросом по `linkId` полей-ссылок. Дерево в памяти, ключи с листа. `count` — размер множества id.
6. Сортировка узлов после сборки, имена одним запросом на уровень. При `KEY_*` и `NAME_*` пустой ключ последний; при `COUNT_*` — только при равенстве `count`.
7. Mapper: полные твины листьев через `TwinRestDTOMapperV2` c `beforeCollectionConversion` при заданном `showTwinMode`; голова и link-твины через `ifDeniedLog`; статус, класс, flavor и data list — из show-режимов запроса.
8. Контроллер `TwinGroupedSearchController`, путь `/private/twin/search/grouped/v1`, `@Operation`, `@ApiResponses`, `@ParametersApiUserHeaders`, `@ProtectedBy`, `@MapperContextBinding`. Параметра пагинации нет.
9. Тесты: S6–S9 на валидации; сборка S1–S3 и S5 из готовых листьев и строк связей (`count` родителя не равен сумме детей, пустой ключ последний). Интеграционный тест — S1, S2, S10, когда в фикстурах есть класс, два исполнителя, два статуса и link.
10. `EXPLAIN` выборки класса и целевой выборки `twin_link`. Миграция индекса — если план показывает seq scan.

## Вне этой работы

- Пагинация и cursor догрузки; потолок 5000 настраивается перекомпиляцией.
- Четвёртый уровень и обход цепочки голов.
- Критерий, который читает поле или связь с твина-узла, а не с листа.
- Пустые группы ради полного справочника статусов, пользователей или связанных твинов.
- Обратные link-поля: остаются за `400`, пока загрузка обратных связей не появится в API с пагинацией.
- Базовые `createdAt` и имя как критерий.
- Count и export этого дерева отдельными endpoint.
