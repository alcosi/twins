# Grouped Twin Search: плоский поиск, собранный в дерево по критерию

Статус: архитектурная постановка для текущей ветки. Домен-пример `wnr` ниже только иллюстрация, идентификаторы в код не переносятся.

## Задача

Клиент отправляет тот же поиск, что и для плоского списка: фильтр `TwinSearchDTOv1`. В ответе лежат те же твины, но собранные в дерево по критерию.

Критерий задаёт узел. Листья всегда твины, прошедшие фильтр. Узел может быть значением поля или связанным твином.

| Критерий | Откуда ключ | Кто является узлом |
| --- | --- | --- |
| Поле | колонка `twin` или значение динамического поля, которое уже умеет `countGroup` | пользователь, статус, класс, опция списка, скаляр |
| Head | `twin.head_twin_id` найденного твина | твин-голова. В фильтре голова уже есть как `headTwinIdList`, здесь она становится узлом, а не условием отбора |
| Link | строка `twin_link` с заданным `linkId` | твин на выбранном конце связи. Найденный твин стоит на другом конце |

Пример поля: фильтр по классу `TASK`, критерий assignee. Узел — пользователь. Внутри — задачи с этим `assigner_user_id`. Задача без исполнителя попадает в узел с пустым ключом.

Пример связи: тот же фильтр по `TASK`, критерий входящего link на тип работ. Узел — твин типа работ. Внутри — задачи, у которых этот link указывает на него. Задача без такого link попадает в пустой ключ. Сам тип работ фильтром не искался и в листьях не лежит.

Плоский `POST /private/twin/search/v4` отдаёт одну страницу тех же твинов. Группирующий поиск возвращает их все, разложенными по дереву. Пагинации и потолка на число листьев нет. Состав листьев совпадает с полным результатом фильтра.

## Глубина

Один критерий даёт один уровень узлов. Под каждым узлом сразу листья. Это и есть глубина 1. Head и link на этом уровне ничем не глубже поля: оба просто раскладывают одну и ту же выборку.

Дерево глубже одного уровня возможно. Глубина равна числу критериев в запросе, сверху вниз. Каждый следующий критерий режет ту же выборку внутри уже полученной группы. Отдельного поиска на уровне нет.

Пример глубины 2: сначала head, внутри assignee, внутри задачи. Проект — голова задачи. Исполнитель — поле той же задачи. Оба ключа читаются с листа, не друг с друга.

Повтор того же head вторым уровнем сам по себе ничего не добавляет: у задачи одна голова. Цепочка «голова головы» — другое чтение. Оно включается числом `depth` на критерии `HEAD`: `depth = 1` — непосредственная голова, `depth = 2` — узел дальней головы, под ним непосредственная, под ней листья. Идти есть куда, потому что у твина не больше одной головы. Цикл обрывается на уже встреченном id. Цепочка короче запрошенной глубины заканчивается раньше, лист всё равно на месте.

У link такого числа глубины нет. Следующий шаг — другая связь, со своим `linkId` и своим концом. Это следующий элемент списка критериев, и читается он уже с твина-узла предыдущего шага, потому что у листа этой связи нет. Ветвление здесь обычное: у одного твина несколько строк одного link, поэтому он стоит в нескольких узлах, как multiple select. Цикл по id тоже обрывается.

Поле следующим шагом после head или link по-прежнему читается с листа. Поле пользователя или поля головы отдельным ходом не становятся.

Итого:

- один критерий — один уровень, листья сразу под узлом;
- список критериев — глубина равна длине списка, листья те же;
- `depth` больше 1 осмыслен только у `HEAD`;
- link углубляется только явным следующим критерием со своим `linkId`.

Потолка на число листьев нет. Потолок на глубину запроса есть: не больше 3 критериев, у `HEAD` не больше `depth = 3`. Это ограничение формы запроса. Глубже при полном ответе link размножает узлы на каждом шаге. Значение вне потолка — 400, выборка не выполняется.

## Поля

Поле группировки законно, если его принимает тот же путь, что `POST /private/twin/count/v1` после `TWINS-857`.

Базовое поле законно, когда `TwinSearchServiceV2.convertToEntityField` возвращает колонку. Динамическое поле законно, когда `TwinFieldStorage.countGroup` возвращает `GroupExpressionProvider`. `null` из `countGroup` даёт 400, `TWIN_SEARCH_CONFIG_INCORRECT`, текст «is not countable». Свой список полей группирующий поиск не заводит.

| `TwinClassFieldId` | Колонка | Кто является узлом |
| --- | --- | --- |
| `00000000-0000-0000-0011-000000000007` assignee | `twin.assigner_user_id` | `User` |
| `00000000-0000-0000-0011-000000000006` owner | `twin.owner_user_id` | `User` |
| creator | `twin.created_by_user_id` | `User` |
| status | `twin.twin_status_id` | `TwinStatus` |
| class | `twin.twin_class_id` | `TwinClass` |
| head | `twin.head_twin_id` | `Twin` (голова) |
| flavor | `twin.flavor_data_list_option_id` | `DataListOption` |

Точные UUID status, class, head, flavor и creator берутся из `SystemIds.TwinClassField.Base`.

Динамические хранилища, у которых `countGroup` уже есть: data list (`dataListOptionId`, для multiple select `isDistinctGroup`), simple, decimal, boolean, timestamp. Хранилища с `countGroup = null`: user, twin, link, i18n, attachment, calc, spirit, space role user, dependent, simple non-index, twin class list. Пользовательское поле-исполнитель в эту выборку входит через колонку `assigner_user_id`. Отдельное dynamic user-поле группой не является.

Колонка `twin` и одиночное динамическое значение кладут твин в одну группу. Multiple select data list хранит несколько строк на твин: твин входит в группу каждой выбранной опции, внутри группы учитывается один раз. Так уже считает `CountQueryExecutor` через `COUNT(DISTINCT)`. Сумма `count` по группам тогда больше числа твинов.

Твин без строки динамического поля попадает в группу с пустым ключом. `countGroup` присоединяет таблицу поля через `LEFT JOIN`, пустое значение остаётся группой, а не выпадает из выборки.

Ключ динамической группы в счётчике лежит в `TwinCountDTOv1.groupedFieldValues` (`twinClassFieldId` → значение). `TwinEntity.groupedFieldValues` — временная карта строки агрегата, на загруженном твине её нет. Узел data list в счётчике остаётся сырым id опции: `TwinCountRestDTOMapper` related object для него не собирает. Группирующий поиск для `workType` догружает опцию списка отдельно, если узел должен быть объектом, а не UUID.

`project-context.md` запрещает группировку по `userId` на сущностях, где ключ почти уникален для каждой строки (пример — `domain_business_account_user`), и требует пагинацию любого неограниченного списка. Для этого endpoint решение другое. Ключ — различные `assigner_user_id` среди твинов, прошедших фильтр, а ответ содержит всю выборку целиком. Потолок на число групп и листьев в контракт не закладывается. Размер ответа определяется фильтром и правами видимости.

## Граница v1

Один критерий и поэтому один уровень узлов.

Критерий v1 — поле (базовое или динамическое по правилу ниже), `HEAD` с `depth = 1` или один `LINK` с `linkId` и концом узла. Список критериев и `HEAD.depth` больше 1 остаются следующей версией: алгоритм тот же, в v1 запрос их отвергает 400.

`TASK.workType` как data list в v1 входит. Dynamic user-поле не входит, пока `TwinFieldStorageUser.countGroup` возвращает `null`. Link-хранилище поля тут ни при чём: критерий `LINK` читает `twin_link`, а `TwinFieldStorageLink.countGroup` как раз возвращает `null`.

Пустые группы не возвращаются. Пользователь без задач, прошедших фильтр, в ответ не попадает. Полный справочник пользователей с нулевыми корзинами собирается запросом к пользователям.

Фильтр применяется к твинам. Группы выводятся из уже отфильтрованной выборки. Невидимый твин не создаёт группу и не увеличивает `count`. Проверка видимости — `TwinSearchServiceV2.createFilterSpecification`.

## Контракт

`POST /private/twin/search/grouped/v1`

Право: `@ProtectedBy({Permissions.TWIN_MANAGE, Permissions.TWIN_VIEW})`.

Query-параметров страницы нет. `@SimplePaginationParams` на метод не вешается.

```json
{
  "search": {
    "twinClassIdList": ["<класс TASK>"]
  },
  "criteria": [
    {
      "type": "FIELD",
      "fieldId": "00000000-0000-0000-0011-000000000007",
      "sort": "NAME_ASC"
    }
  ],
  "memberSorts": [
    { "twinClassFieldId": "<createdAt>", "direction": "DESC" }
  ]
}
```

Тот же поиск, собранный по link. `nodeEnd = DST` значит, что узел — `dst_twin_id`, а лист — `src_twin_id` этой связи:

```json
{
  "search": { "twinClassIdList": ["<класс TASK>"] },
  "criteria": [
    { "type": "LINK", "linkId": "<link>", "nodeEnd": "DST", "sort": "NAME_ASC" }
  ],
  "memberSorts": []
}
```

`search` — `TwinSearchDTOv1`, тот же фильтр, что у плоского поиска. Сортировки в `search` нет. Критерий в фильтр не входит: `headTwinIdList` и отбор по link по-прежнему сужают выборку, а `criteria` только раскладывают то, что после фильтра осталось.

В v1 в `criteria` ровно один элемент. Пустой список и длина больше 3 — 400. `FIELD` без законного `fieldId`, `LINK` без `linkId` или без `nodeEnd`, `HEAD` с `depth` вне 1..3 — 400. Базовое поле вне семи колонок и динамическое поле с `countGroup = null` — 400, `TWIN_SEARCH_CONFIG_INCORRECT`.

`HEAD` в v1 приходит как `{ "type": "HEAD", "depth": 1, "sort": "NAME_ASC" }`. `depth` больше 1 в v1 — 400.

`sort` критерия:

| Значение | Порядок групп |
| --- | --- |
| `NAME_ASC` / `NAME_DESC` | Отображаемое имя ключа. Для assignee, owner, creator — `user.name`. Для head — `twin.name`. Для status, class, flavor имя лежит в i18n, в v1 такие значения дают 400 |
| `COUNT_DESC` / `COUNT_ASC` | Размер группы, затем id ключа по возрастанию |
| `KEY_ASC` / `KEY_DESC` | Сырой UUID ключа. Пустой ключ всегда последний |

По умолчанию для пользовательских полей и head — `NAME_ASC`. Для status, class, flavor — `KEY_ASC`.

`memberSorts` — до двух полей, `TwinSortDTOv1` и `TwinSearchServiceV2.createSortSpecification`. Пустой список — `createdAt DESC`, затем `id ASC`.

Ответ содержит каждую группу выборки и каждый её твин. `count` равен длине `twins` этой группы.

```json
{
  "groupFieldId": "00000000-0000-0000-0011-000000000007",
  "groups": [
    {
      "assignerUserId": "<user>",
      "count": 42,
      "twins": [ { } ]
    },
    {
      "assignerUserId": null,
      "count": 3,
      "twins": [ { } ]
    }
  ],
  "relatedObjects": { }
}
```

Ключ группы заполняется так же, как в `TwinCountDTOv1`: присутствует только запрошенное поле. `assignerUserId = null` — одна группа «без исполнителя» на всю выборку. Related objects резолвят пользователя, статус, класс, голову и flavor тем же путём, что `TwinCountRestDTOMapper`. Листья — `TwinDTOv2`.

## Как выполняется запрос

Один SELECT, одна read-only транзакция. Запрос забирает все видимые твины фильтра с сортировкой листьев. `LIMIT` и `OFFSET` в него не ставятся. Сервис раскладывает строки по значению поля группировки. Пустое значение собирается в одну группу. `count` считается по собранному списку.

Отдельный `GROUP BY` нужен был бы, если бы листья резались, а размер группы надо было знать заранее. Здесь состав группы и её размер видны по самим строкам.

Сортировка групп выполняется после сборки. Для `NAME_*` пользователи и головы догружаются одним пакетом, затем группы упорядочиваются по имени. Пустой ключ ставится последним и при `NAME_*`, и при `KEY_*`. `COUNT_*` сравнивает размеры уже собранных групп, затем id ключа.

Листья пакетом догружает mapper твина через `beforeCollectionConversion`. Ключи пакетом грузит mapper по образцу `TwinCountRestDTOMapper`, только для типа, который соответствует `groupFieldId`.

Индекс. Выборка всех задач класса по домену без подходящего индекса читает `twin` целиком. Кандидат: `(domain_id, twin_class_id, assigner_user_id)`. Такой же кандидат для status и head, когда эти сценарии подтвердятся. Миграция добавляется после `EXPLAIN` на dev-объёме `wnr`, если план показывает seq scan или sort по всей таблице. Ответ при этом всё равно полный: индекс ускоряет выборку и не ограничивает её.

## Сценарии

Идентификаторы `wnr` нужны, чтобы сценарий можно было прогнать руками. В код они не попадают.

Операционный `TASK` домена `wnr`: `7c027b60-0f6c-445c-9889-8ee3855d2c59`. Исполнитель — колонка `assigner_user_id`.

### S1. Задачи по исполнителю

Фильтр: класс `TASK`. `groupFieldId` — assignee. `groupSort = NAME_ASC`. `memberSorts` — `createdAt DESC`.

Ожидание:

- в ответе есть группа на каждого исполнителя, у которого есть хотя бы одна видимая задача фильтра;
- в `relatedObjects` есть пользователь каждого такого id;
- каждый лист имеет класс `TASK` и того же исполнителя, что ключ группы;
- листья одной группы отсортированы по `createdAt DESC`;
- группы идут по `user.name`;
- `count` группы равен числу её листьев;
- сумма `count` по группам равна числу видимых задач фильтра, включая задачи без исполнителя.

### S2. Задачи без исполнителя

В выборке есть `TASK` с `assigner_user_id IS NULL`.

Ожидание: одна группа с `assignerUserId = null`, без пользователя в related objects. Она последняя и при `NAME_ASC`, и при `KEY_ASC`. Её листья — задачи без исполнителя.

### S3. Фильтр сужает группы

Тот же S1 плюс фильтр, который оставляет задачи одного статуса.

Ожидание: исполнитель, у которого не осталось задач этого статуса, отсутствует в `groups`. `count` считается после фильтра и равен числу оставшихся листьев этой группы. Сумма `count` равна числу задач, прошедших фильтр.

### S4. Группа больше обычной страницы поиска

У одного исполнителя задач больше, чем типичный размер страницы плоского поиска.

Ожидание: в `twins` лежат все его задачи фильтра. `count` равен этому числу. Остальные группы тоже присутствуют целиком.

### S5. Много групп

Различных исполнителей больше, чем типичный размер страницы.

Ожидание: один ответ содержит все группы. Повторный запрос с тем же телом возвращает тот же состав. Отдельной второй страницы у endpoint нет.

### S6. Группировка по статусу

`groupFieldId` — status. `groupSort = KEY_ASC`. `NAME_ASC` на этом поле даёт 400.

Ожидание: узел — `twinStatusId`, статус приходит через related objects. Листья — те же `TASK`. Группа с пустым ключом появляется, только если колонка допускает NULL.

### S7. Группировка по голове

Критерий `HEAD`, `depth = 1`. Фильтр по-прежнему класс `TASK`.

Ожидание: узел — твин `headTwinId`. Для операционного `wnr` это проект. Листья — задачи с этой головой. Проект в листья не попадает: его не было в фильтре. Задача лежит в группе своего `head_twin_id`. Голова, которую пользователю нельзя читать, остаётся id узла без тела твина: сам id и так есть на листе.

### S13. Группировка по link

Критерий `LINK`, один `linkId`, `nodeEnd = DST`. Фильтр — класс `TASK`.

Ожидание: узел — `dst_twin_id` этой связи. Листья — задачи из фильтра, стоящие на `src`. Задача с двумя такими связями входит в оба узла по одному разу. Задача без связи входит в пустой ключ. Другие link этой задачи узлов не создают. Сумма `count` больше числа задач, если хотя бы одна задача попала в два узла.

### S8. Невидимая задача

У пользователя нет права видеть часть `TASK`.

Ожидание: эти твины отсутствуют в листьях и в `count`. Группа, у которой видимых задач не осталось, отсутствует. Ответ 200.

### S9. Негруппируемое поле

`groupFieldId` — базовые имя или `createdAt`, либо динамическое поле хранилища с `countGroup = null` (user, link, i18n и остальные из списка выше).

Ожидание: 400, `TWIN_SEARCH_CONFIG_INCORRECT`. Запрос за твинами не выполняется.

Data list, simple, decimal, boolean и timestamp эту ошибку не получают.

### S10. Сортировка групп и листьев независимы

`groupSort = COUNT_DESC`, `memberSorts` — имя по возрастанию.

Ожидание: первой идёт самая большая группа. Внутри группы листья идут по имени.

### S11. Тип работ как поле задачи

Операционный `TASK.workType` (`95f2c8ca-8b79-4971-9726-270a11c7d031`) хранится в `twin_field_data_list`. Это значение поля задачи, отдельного твина типа работ в выборке нет.

`TwinFieldStorageDatalist.countGroup` уже группирует по `dataListOptionId`. Узел — опция списка, листья — задачи с этой опцией. Задача без значения поля попадает в группу с пустым ключом. Multiple select кладёт задачу в каждую выбранную опцию. Сумма `count` для одиночного выбора равна числу задач фильтра.

### S12. Вложенная группировка

Запрос «исполнитель → статус → задачи» в v1 не принимается: поля группировки одно. До фазы 3 клиент получает один уровень и при необходимости сужает статус фильтром `search` на весь ответ.

## Задачи реализации

Общие части с плоским поиском — фильтр, сортировка и пакетная подгрузка твинов из `TwinSearchServiceV2`.

### Фаза 1. Один уровень

Поле, `HEAD` глубины 1 или один `LINK`. Ответ полный.

1. DTO запроса `TwinGroupedSearchRqDTOv1`: `search` (`TwinSearchDTOv1`), `criteria` (в v1 размер ровно 1), `memberSorts` (`@Size(max = 2)`). Элемент критерия: `type` (`FIELD`, `HEAD`, `LINK`), для поля `fieldId`, для link `linkId` и `nodeEnd`, для head `depth`, плюс `sort`. Полей лимита и страницы в теле нет.
2. DTO группы и ответа. Ключевые поля группы совпадают с `TwinCountDTOv1`, плюс `count` и `twins` (`List<TwinDTOv2>`). Ответ расширяет `ResponseRelatedObjectsDTOv1`. Блока `pagination` в нём нет.
3. Доменные объекты запроса и результата. DTO в сервис не протекают, сущности в JSON не сериализуются.
4. Валидация через `TwinSearchServiceV2.resolveGroupProviders`: базовая колонка или `countGroup`. Поле с `countGroup = null` — 400 до выборки. `NAME_*` для status, class, flavor и для динамического ключа, чьё имя лежит в i18n, — 400 до запроса. Для data list опция имеет i18n-имя, поэтому в v1 её `groupSort` — `KEY_ASC` или `COUNT_*`.
5. Сервис `TwinGroupedSearchService.search`, read-only транзакция. Один вызов выборки всех твинов фильтра с сортировкой листьев, без `Pageable`. `FIELD` по колонке твина или по значению storage. `HEAD` глубины 1 — по `headTwinId`, узел догружается пакетом как твин. `LINK` — один запрос строк `twin_link` по id листьев, `linkId` и концу узла; лист с несколькими строками входит в несколько групп. Пустой ключ — отдельная группа. Повторный `GROUP BY` с `LIMIT` не строится.
6. Сортировка групп в памяти: `COUNT_*` по размеру, `KEY_*` по UUID, `NAME_*` по пакетно загруженному `user.name` или `twin.name`. Пустой ключ последний.
7. `count` проставляется длиной списка группы. Для однозначного поля сумма `count` равна числу твинов выборки. Для multiple select сумма больше, каждый твин внутри одной опции встречается один раз.
8. Mapper листьев — mapper твина с `beforeCollectionConversion`. Базовый ключ грузит user, status, class, head или flavor по образцу `TwinCountRestDTOMapper`. Динамический ключ отдаётся как `groupedFieldValues`. Для data list опция дополнительно кладётся в related objects: счётчик этого не делает.
9. Контроллер `TwinGroupedSearchController`, путь `/private/twin/search/grouped/v1`, аннотации `@Operation`, `@ApiResponses`, `@ParametersApiUserHeaders`, `@ProtectedBy`, `@MapperContextBinding`. Параметра пагинации нет.
10. Тесты валидации (S9, запрет `NAME_ASC` для статуса) и тесты сборки ответа из уже полученных твинов (порядок групп и листьев, пустой ключ последний, `count` равен размеру группы). Интеграционный тест на Testcontainers — S1, S2, S4, S5, S8, когда в фикстурах есть права и два исполнителя. S4 и S5 проверяют, что в ответе нет отброшенных строк.
11. `EXPLAIN` полной выборки задач класса по assignee. Миграция индекса — если план показывает seq scan или sort по всей `twin`.

### Фаза 2. Динамический ключ в том же endpoint

Отдельный join не пишется: его уже отдаёт `countGroup`. Фаза добавляет чтение значения и сборку узла.

12. После полной выборки твинов загрузить storage поля через существующий batch-load. Группировать по значению колонки, которую группирует `countGroup`: `dataListOptionId`, `value` у simple, decimal, boolean, timestamp.
13. Multiple select: твин в каждой выбранной опции, один раз на опцию. Тест на data list с двумя опциями у одной задачи.
14. Твин без строки поля — группа с пустым ключом, вместе с остальными листьями фильтра.
15. Сценарий `TASK.workType`: узел — `dataListOptionId` в `groupedFieldValues`, опция в related objects, листья — задачи с этой опцией.
16. Хранилище с `countGroup = null`, включая dynamic user, остаётся 400. Новый `countGroup` для него в эту задачу не входит.
17. `EXPLAIN` выборки с последующей загрузкой `twin_field_data_list` по id твинов. Миграция — если план показывает seq scan.

### Фаза 3. Глубина больше одного уровня

Тот же endpoint. В v1 массив `criteria` длиной не 1 отвергается.

18. Принять от 2 до 3 критериев. Листья по-прежнему одна полная выборка фильтра. Каждый критерий читает ключ с листа, кроме `LINK`/`HEAD`, который стоит в списке после другого `LINK`/`HEAD`: такой шаг читает ключ с твина предыдущего узла.
19. `twins` есть только на последнем уровне. Верхний узел содержит вложенные группы, `count` и свой ключ. `count` верхнего узла — число листьев фильтра в его поддереве, с учётом повтора листа в нескольких ветках link и multiple select.
20. У каждого критерия свой `sort`. Лимита на число узлов ответа нет.
21. `HEAD.depth` 2 и 3 строит цепочку голов от листа вверх. Повторенный id обрывает цепочку. Недостающую голову лист не теряет: цепочка короче запрошенной.
22. Приёмка поля: assignee, внутри статус, внутри все задачи. Приёмка связи: `LINK`, внутри `HEAD` этого узла, внутри все задачи этой связи. Пустой ключ на каждом уровне следует правилу S2.

## Вне этой работы

- Пагинация групп, лимит листьев, флаг `truncated` и отдельный cursor догрузки. Дерево возвращается целиком.
- Пустые группы ради полного справочника пользователей или статусов.
- Базовые `createdAt` и имя. У счётчика они по-прежнему не группируются. Динамические simple, decimal и timestamp группируются, потому что `countGroup` их уже разрешает: полное дерево на таком поле может дать группу на каждое значение.
- Count и export этой выборки отдельными endpoint.
- Новый `countGroup` для хранилищ, которые сейчас возвращают `null`.
