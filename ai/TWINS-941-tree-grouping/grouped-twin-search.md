# Grouped Twin Search: плоский поиск одного класса, дерево глубины 3

Статус: архитектурная постановка для текущей ветки. Домен-пример `wnr` ниже только иллюстрация, идентификаторы в код не переносятся.

## Задача

Сначала выполняется плоский поиск твинов одного класса. Затем эти же твины раскладываются в дерево глубиной до 3. Каждый уровень — группировка по полю или по link. Листья — твины плоского поиска, других твинов поиск не добавляет.

Порядок уровней задаёт клиент. Пример, не фиксированная схема: первый уровень — статус, второй — assignee, третий — link. На месте статуса может стоять другое поле, link может стоять на любом из трёх уровней.

Узел поля — значение этого поля у листа. Для статуса это статус, для assignee — пользователь, для data list — опция. Узел link — твин на выбранном конце заданной связи. Сам связанный твин в плоский поиск не входил и листом не становится.

Задача без исполнителя, без значения поля или без строки этого link остаётся в группе с пустым ключом на соответствующем уровне. Так в дереве сохраняются все твины плоского поиска.

`POST /private/twin/search/v4` возвращает ту же выборку постранично. Этот endpoint возвращает её целиком, уже разложенной. Пагинации и потолка на число листьев нет.

## Глубина

В запросе от 1 до 3 критериев, сверху вниз. Глубина ответа равна длине списка. Три уровня — обязательная возможность. Один и два уровня собираются тем же алгоритмом: последний критерий несёт листья, верхние несут вложенные группы.

Все критерии читают ключ с листа, то есть с твина плоского поиска. Статус, assignee и link из примера — свойства одной и той же задачи. Следующий уровень не переключается на твин-узел предыдущего уровня и не идёт к голове головы.

Голова отдельным типом критерия не задаётся. Группировка по голове — это поле `head` (`twin.head_twin_id`): узел — твин-голова листа. Цепочка из нескольких голов в эту задачу не входит.

Одинаковый критерий дважды — 400. Два link допустимы, если у них разные `linkId` или разный конец узла.

Длина списка 0 или больше 3 — 400, выборка не начинается.

## Как режется один лист

Поле с одним значением кладёт лист в один узел. Колонки `twin` такие. Динамическое поле с несколькими строками и link с несколькими строками кладут лист в несколько узлов этого уровня.

`count` узла — число различных листьев в его поддереве. Задача с двумя link одного критерия даёт два узла на уровне link и единицу в `count` статуса и assignee. Сумма `count` детей может быть больше `count` родителя. Сумма `count` корней равна числу твинов плоского поиска: пустые ключи не выкидывают лист.

## Поле

Поле законно, если его принимает `POST /private/twin/count/v1`.

Базовое поле законно, когда `TwinSearchServiceV2.convertToEntityField` возвращает колонку. Динамическое законно, когда `TwinFieldStorage.countGroup` возвращает выражение. `null` даёт 400, `TWIN_SEARCH_CONFIG_INCORRECT`.

| Поле | Колонка | Узел |
| --- | --- | --- |
| assignee `00000000-0000-0000-0011-000000000007` | `twin.assigner_user_id` | пользователь |
| owner `00000000-0000-0000-0011-000000000006` | `twin.owner_user_id` | пользователь |
| creator | `twin.created_by_user_id` | пользователь |
| status | `twin.twin_status_id` | статус |
| class | `twin.twin_class_id` | класс |
| head | `twin.head_twin_id` | твин-голова |
| flavor | `twin.flavor_data_list_option_id` | опция списка |

Остальные UUID берутся из `SystemIds.TwinClassField.Base`.

Динамические хранилища с `countGroup`: data list (multiple select помечает `isDistinctGroup`), simple, decimal, boolean, timestamp. Хранилища с `countGroup = null`: user, twin, link, i18n, attachment, calc, spirit, space role user, dependent, simple non-index, twin class list. Поле-исполнитель класса user сюда не входит. Исполнитель задачи входит как колонка assignee. Link-поле класса не заменяет критерий `LINK`.

## Link

Критерий задаёт `linkId` и `nodeEnd`.

| `nodeEnd` | Узел | Лист |
| --- | --- | --- |
| `DST` | `twin_link.dst_twin_id` | `twin_link.src_twin_id` |
| `SRC` | `twin_link.src_twin_id` | `twin_link.dst_twin_id` |

Берутся строки с этим `linkId`, у которых конец листа входит в плоскую выборку. Другие связи листа узлов не создают. Несколько строк кладут лист в несколько узлов. Ноль строк — пустой ключ.

`TwinFieldStorageLink.countGroup` возвращает `null` и этот критерий не описывает.

## Контракт

`POST /private/twin/search/grouped/v1`

Право: `@ProtectedBy({Permissions.TWIN_MANAGE, Permissions.TWIN_VIEW})`.

Параметров страницы нет.

```json
{
  "search": {
    "twinClassIdList": ["<один класс, например TASK>"]
  },
  "criteria": [
    { "type": "FIELD", "fieldId": "<status>", "sort": "KEY_ASC" },
    { "type": "FIELD", "fieldId": "00000000-0000-0000-0011-000000000007", "sort": "NAME_ASC" },
    { "type": "LINK", "linkId": "<link>", "nodeEnd": "DST", "sort": "NAME_ASC" }
  ],
  "memberSorts": [
    { "twinClassFieldId": "<createdAt>", "direction": "DESC" }
  ]
}
```

`search` — `TwinSearchDTOv1`. В нём ровно один id в `twinClassIdList`. Остальные условия плоского поиска сужают выборку до группировки. Пустой список классов и больше одного класса — 400. Сортировки в `search` нет.

`criteria` — от 1 до 3 элементов. `FIELD` проверяется правилом поля. `LINK` требует `linkId` и `nodeEnd`.

`sort` уровня:

| Значение | Порядок узлов |
| --- | --- |
| `NAME_ASC` / `NAME_DESC` | Имя ключа. Assignee, owner, creator — `user.name`. Head и узел link — `twin.name`. Status, class, flavor и data list в этом режиме — 400: имя лежит в i18n |
| `COUNT_DESC` / `COUNT_ASC` | `count` узла, затем id ключа |
| `KEY_ASC` / `KEY_DESC` | UUID ключа. Пустой ключ последний |

Для пользовательских полей, head и link по умолчанию `NAME_ASC`. Для status, class, flavor и data list — `KEY_ASC`.

`memberSorts` — до двух полей, `TwinSortDTOv1` и `TwinSearchServiceV2.createSortSpecification`. Пустой список — `createdAt DESC`, затем `id ASC`. Сортировка листьев не переставляет узлы.

Ответ на примере выше:

```json
{
  "groups": [
    {
      "twinStatusId": "<статус>",
      "count": 10,
      "groups": [
        {
          "assignerUserId": "<пользователь>",
          "count": 4,
          "groups": [
            {
              "linkId": "<link>",
              "linkTwinId": "<dst>",
              "count": 2,
              "twins": [ { } ]
            }
          ]
        }
      ]
    }
  ],
  "relatedObjects": { }
}
```

На последнем уровне лежит `twins`. На верхних — `groups`. При одном критерии корни сразу содержат `twins`. При двух — вложенность из двух групп.

Ключ поля заполняется как в `TwinCountDTOv1`: одно запрошенное поле. Динамическое значение — `groupedFieldValues`. Ключ link — `linkId` и `linkTwinId`. Пустой ключ оставляет эти поля пустыми. `count` — число различных листьев поддерева.

Related objects резолвят пользователя, статус, класс, голову, flavor и твин link. Опцию data list этот путь догружает отдельно: счётчик её в related objects не кладёт.

Невидимый твин не входит в выборку и не создаёт узлы. Твин на конце link, который нельзя прочитать, остаётся id узла без тела: id и так известен по строке связи.

## Как выполняется запрос

Одна read-only транзакция.

1. Все твины одного класса по фильтру, с сортировкой листьев, без `Pageable`.
2. Пакетная загрузка значений тех полей из `criteria`, которых нет на самой строке `twin`.
3. Один запрос `twin_link` по id листьев и по всем `linkId` из критериев.
4. Сборка дерева в памяти. Ключ каждого уровня считается по листу. Пустое значение — своя группа. Повтор листа на уровне link или multiple select размножает только этот уровень.
5. `count` пересчитывается по множеству id листьев поддерева.
6. Узлы уровня сортируются своим `sort`. Пустой ключ последний.

`GROUP BY` счётчика для ответа не используется: он не возвращает листья. `countGroup` нужен как проверка поля.

Индекс. Выборка класса по домену и выборка связей по `src_twin_id` или `dst_twin_id` плюс `link_id`. Миграция — после `EXPLAIN` на объёме `wnr`, если план показывает seq scan. Индекс не ограничивает полноту ответа.

## Сценарии

Операционный `TASK` домена `wnr`: `7c027b60-0f6c-445c-9889-8ee3855d2c59`. Идентификаторы в код не переносятся.

### S1. Статус, assignee, link

Фильтр: один класс `TASK`. Критерии: status `KEY_ASC`, assignee `NAME_ASC`, link `DST` и `NAME_ASC`. Листья — `createdAt DESC`.

Ожидание:

- корни — статусы задач фильтра, по UUID статуса;
- внутри статуса — исполнители этих задач, по `user.name`;
- внутри исполнителя — `dst` заданного link, по `twin.name`;
- листья под link — задачи с этим статусом, исполнителем и `dst`;
- задача другого класса отсутствует;
- сумма `count` корней равна числу задач фильтра.

### S2. Пустые ключи

Есть задача без assignee и задача без строки этого link.

Ожидание: под своим статусом есть узел assignee с пустым id, последним при `NAME_ASC` и `KEY_ASC`. Под исполнителем есть узел link с пустым `linkTwinId`. Обе задачи присутствуют. Остальные уровни для них заполнены своими значениями.

### S3. Несколько link у одной задачи

У задачи два `dst` одного `linkId`. Статус и assignee те же.

Ожидание: два узла link, в каждом эта задача один раз. `count` assignee и `count` статуса считают её один раз. Сумма `count` узлов link больше `count` assignee.

### S4. Фильтр до группировки

К S1 добавлено условие плоского поиска, оставляющее один статус.

Ожидание: в корнях один статус. Исполнители и link посчитаны только по оставшимся задачам.

### S5. Короче трёх уровней

Один критерий assignee. Два критерия: status, затем assignee.

Ожидание: при одном критерии у корня сразу `twins`. При двух `twins` лежат на втором уровне. Набор листьев тот же, что у плоского поиска этого фильтра.

### S6. Четвёртый критерий

В `criteria` четыре элемента.

Ожидание: 400, выборка не выполняется.

### S7. Класс

`twinClassIdList` пуст или содержит два id.

Ожидание: 400.

### S8. Негруппируемое поле

В любом из трёх слотов — имя, `createdAt` или динамическое поле с `countGroup = null`.

Ожидание: 400, `TWIN_SEARCH_CONFIG_INCORRECT`. Data list, simple, decimal, boolean и timestamp проходят.

### S9. Повтор критерия

Два раза один `fieldId`. Два раза один и тот же `linkId` с тем же `nodeEnd`.

Ожидание: 400. Два разных `linkId` на двух уровнях — обычное дерево.

### S10. Невидимая задача

Часть задач фильтра пользователю не видна.

Ожидание: их нет ни на одном уровне и ни в одном `count`. Узел, под которым не осталось видимых задач, отсутствует. Ответ 200.

### S11. Тип работ как поле

`TASK.workType` (`95f2c8ca-8b79-4971-9726-270a11c7d031`) — data list. Он ставится критерием `FIELD` на любом уровне.

Ожидание: узел — `dataListOptionId` в `groupedFieldValues`, опция в related objects. Это не link и не отдельный твин типа работ.

### S12. Сортировки не смешиваются

Корни `COUNT_DESC`, листья по имени.

Ожидание: первым идёт статус с наибольшим числом различных задач. Внутри link листья идут по имени.

## Задачи реализации

1. DTO запроса: `search` (`TwinSearchDTOv1`), `criteria` (`@Size(min = 1, max = 3)`), `memberSorts` (`@Size(max = 2)`). Элемент критерия: `type` (`FIELD` или `LINK`), `fieldId` либо `linkId` вместе с `nodeEnd`, `sort`.
2. DTO узла: ключевые поля как у `TwinCountDTOv1`, `groupedFieldValues`, `linkId`, `linkTwinId`, `count`, `groups`, `twins`. `twins` заполняется только на последнем уровне. Ответ расширяет `ResponseRelatedObjectsDTOv1`. Блока `pagination` нет.
3. Доменные объекты. DTO в сервис не протекают, сущности в JSON не сериализуются.
4. Валидация до выборки: один класс, длина критериев, уникальность критерия, поле через `resolveGroupProviders`, link через существующую проверку id связи, запрет `NAME_*` для ключей с i18n-именем.
5. `TwinGroupedSearchService.search`, read-only. Полная выборка класса без `Pageable`. Поля пакетом через storage. Связи одним запросом по id листьев и `linkId` критериев. Дерево в памяти, ключи с листа. `count` — размер множества id.
6. Сортировка узлов после сборки. Имена пользователей и твинов link/head догружаются пакетом. Пустой ключ последний.
7. Mapper листьев — mapper твина с `beforeCollectionConversion`. Ключи полей — по образцу `TwinCountRestDTOMapper`. Data list и твин link дополнительно в related objects.
8. Контроллер `TwinGroupedSearchController`, путь `/private/twin/search/grouped/v1`, `@Operation`, `@ApiResponses`, `@ParametersApiUserHeaders`, `@ProtectedBy`, `@MapperContextBinding`. Параметра пагинации нет.
9. Тесты: S6–S9 на валидации; сборка S1–S3 и S5 из готовых листьев и строк link (`count` родителя не равен сумме детей, пустой ключ последний). Интеграционный тест — S1, S2, S10, когда в фикстурах есть класс, два исполнителя, два статуса и link.
10. `EXPLAIN` выборки класса и выборки `twin_link` по листьям. Миграция индекса — если план показывает seq scan.

## Вне этой работы

- Пагинация, лимит листьев, `truncated`, cursor догрузки.
- Четвёртый уровень и обход цепочки голов.
- Критерий, который читает поле или link с твина-узла, а не с листа.
- Пустые группы ради полного справочника статусов, пользователей или связанных твинов.
- Базовые `createdAt` и имя как критерий.
- Новый `countGroup` для хранилищ, которые возвращают `null`.
- Count и export этого дерева отдельными endpoint.
