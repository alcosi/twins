# Grouped Twin Search: мнение по постановке

Дата: 2026-11-11. Разбор текущей редакции `grouped-twin-search.md` по коду после `TWINS-857`: `TwinSearchServiceV2.resolveGroupProviders`, `TwinFieldStorage.countGroup`, `GroupExpressionProvider`, `TwinCountDTOv1.groupedFieldValues`.

## Вывод

Граница полей теперь совпадает со счётчиком, и это правильный способ не завести второй белый список. Базовая колонка идёт через `convertToEntityField`. Динамическое поле законно, только если `countGroup` вернул провайдер. `null` даёт `TWIN_SEARCH_CONFIG_INCORRECT` и текст «is not countable». Список хранилищ в постановке совпадает с кодом: data list, simple, decimal, boolean, timestamp группируются; user, twin, link, i18n, attachment, calc, spirit, space role user, dependent, simple non-index и twin class list возвращают `null`. Multiple select и пустое значение описаны так же, как `countGroup`: `LEFT JOIN`, для multiple select `isDistinctGroup()`, твин без строки остаётся группой.

`TASK.workType` в v1 уместен. Отдельный SQL для него не нужен: значение читается тем же kit, которым поле уже грузится на карточку, а провайдер только отвечает «это поле можно группировать».

К реализации я бы перешёл после четырёх правок в тексте. Три старые ошибки на месте, и расширение на dynamic ломает формулировку `KEY_*` как сортировки по UUID.

## Что в тексте всё ещё неверно

Пустой базовый ключ в примере (`"assignerUserId": null`) в JSON не появится. В проекте `spring.jackson.default-property-inclusion = NON_NULL`, и null-свойство DTO вырезается. Для динамического ключа null внутри `groupedFieldValues` как раз доезжает: включение null касается свойств, а не значений карты. Пустую группу data list стоит явно писать как `groupedFieldValues: { "<fieldId>": null }`. Пустую группу assignee — полем, у которого сериализация null включена отдельно. Иначе S2 нечем отличить от потерянного ключа.

Индекс `(domain_id, twin_class_id, assigner_user_id)` по-прежнему невозможен: колонки `domain_id` на `twin` нет. Кандидат для S1 — `(twin_class_id, assigner_user_id)`.

Flavor счётчик не резолвит. `TwinCountRestDTOMapper` грузит user, status, class и head. Ветки flavor нет ни в mapper, ни в `TwinCountDTOv1`. Фраза «flavor тем же путём, что mapper» описывает несуществующий код. Загрузку `DataListOption` для flavor надо описать так же, как для `workType`: отдельно от счётчика.

`GroupExpressionProvider` не отдаёт имя колонки. У него есть `apply(...)`, которому нужен Criteria root, и `isDistinctGroup()`. Имени атрибута там нет. В группирующем поиске провайдер — проверка до выборки и признак multiple select. Само значение берётся из kit storage. Вызывать `apply`, чтобы узнать колонку, не нужно: это тот join, от которого постановка отказалась.

## Сортировка ключа

Таблица `groupSort` по-прежнему определяет `KEY_*` как сырой UUID. Пункт реализации сортирует `KEY_*` по UUID. Для simple, decimal, boolean и timestamp значение другого типа. Приведение к UUID упадёт. `KEY_*` — сравнение сырого значения ключа в его естественном порядке: UUID, строка, число, boolean, timestamp. Пустой ключ последний при любом `groupSort`, включая `COUNT_*`. При равном `count` тай-брейк — то же сырое значение, а не «id ключа», потому что у decimal и timestamp id нет.

Дефолт задан для пользователя, head, status, class и flavor. Для data list, simple, decimal, boolean и timestamp его нет. Data list в пункте 4 уже ограничен `KEY_ASC` и `COUNT_*`, потому что имя опции в i18n. Тот же дефолт `KEY_ASC` стоит записать для всех динамических ключей. `NAME_*` для них — 400, кроме случая, когда имя — это колонка `user.name` или `twin.name`.

Пустой `memberSorts` — `createdAt DESC`, затем `id ASC`. Один `createSortSpecification(createdAt, DESC)` второй ключ не добавляет. Его дописывает сам группирующий сервис. Внутри группы идентичность листа — `twin.id`: фильтр прав и сортировка с join могут вернуть одну строку несколько раз, а сумма `count` в пункте 7 сверяется с числом твинов, не строк.

У `NAME_*` при одинаковом `user.name` нужен тай-брейк по id ключа. S5 фиксирует состав повторного ответа. Порядок групп при равных именах без тай-брейка не зафиксирован.

## Размер ответа

Потолок по-прежнему сознательно не закладывается. С динамическими полями это уже не только «все задачи класса». Simple, decimal и timestamp постановка сама называет полями, где группа может возникнуть на каждое значение. Легальный запрос с пустым `search` и группировкой по timestamp возвращает все видимые твины домена, почти по одному в группе, каждый как `TwinDTOv2`.

Частичное дерево по-прежнему хуже полного. С контрактом согласуется отказ: если различных твинов больше порога, 400, без урезанного JSON. Порог особенно нужен полям высокой кардинальности, которые v1 теперь принимает.

`search` остаётся `TwinSearchDTOv1`, без `headSearch` и `childrenSearch`, которые есть у счётчика и поиска v4. Если это ограничение продукта, его достаточно одной фразы. Сейчас это выглядит как свойство выбранного типа.
