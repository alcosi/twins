# Версионирование настроек домена — модель v2 (штампы версий + row_status)

Статус: модель согласована (2026-10-15/16): пример, rollback, LOCK, ленивое открытие версий,
механика удалений row_status. Развивает `domain-versioning-handoff.md`; реализация — пилотный
план `domain-versioning-slice-a.md` (переписан по модели v2, 2026-10-16). Открытых вопросов нет.

## Модель — двумя словами

В каждой настроечной таблице у строки есть два служебных поля:

- **Штамп версии** (`domain_version_id`) — «версия, которая последней добавила, изменила или удалила эту строку»;
- **Статус строки** (`row_status`) — `ACTIVE` (рабочая), `DISABLED` (временно отключена), `DELETED` (помечена на удаление, физически удаляется при релизе).

Версия — это строка в `domain_version`. Пока идёт редактирование, версия открыта (OPEN, метка
`draft`). Все операции вставки/изменения/удаления штампуют строки её идентификатором. Релиз
замораживает версию (RELEASED, финальная метка), физически удаляет DELETED-строки — и **не
открывает следующую версию**. Домен продолжает указывать на RELEASED-версию; **первая же правка
после релиза создаёт новую OPEN-версию с новым UUID** (ленивое открытие) — дальнейшие правки
штампуют уже её. Поэтому статус текущей версии сам отвечает на вопрос «правили ли конфиг»:

- `domain.current_domain_version_id` → RELEASED — правок нет, содержимое домена в точности равно
  снапшоту этого релиза;
- → OPEN — в домене есть несрелизованные правки.

`current_domain_version_id` — NOT NULL: домен рождается сразу с версией V1 (OPEN, пустой), её
создаёт триггер after-insert на `domain`. Ленивое открытие касается только окон ПОСЛЕ релизов.

Никакого отдельного флага чистоты не нужно.

Рабочий пример: настроечная таблица `TableA`, домен только что создан, в нём три строки.

## Схема (DDL)

### Таблица `domain_version`

```sql
CREATE TABLE domain_version (
    id                         uuid PRIMARY KEY,          -- uuid_generate_v7_custom()
    domain_id                  uuid NOT NULL REFERENCES domain
                                   ON UPDATE CASCADE ON DELETE CASCADE DEFERRABLE INITIALLY DEFERRED,
    version                    varchar NOT NULL,          -- OPEN-окно: 'draft'; релиз: финальный лейбл;
                                                              -- импорт: например '(import) 1.2'
    name                       varchar,
    description                varchar,
    status                     varchar NOT NULL DEFAULT 'OPEN'
                                   CHECK (status IN ('OPEN','RELEASED')),
    "order"                    bigint,                    -- монотонный счётчик домена; присваивается при релизе
                                                              -- и импорте, у открытого окна NULL; сортировка/walk цепочки
    json_file                  jsonb,                     -- полный снапшот состояния (у импорта — опционально)
    hash                       varchar,                   -- SHA-256 полного состояния; у релиза и импорта — всегда
    delta_file                 jsonb,                     -- прямая дельта prev → этот релиз (инкрементальный импорт
                                                              -- между средами); NULL у первого релиза
    delta_hash                 varchar,
    rollback_delta_file        jsonb,                     -- обратная дельта этот релиз → prev (локальный возврат)
    rollback_delta_hash        varchar,
    previous_domain_version_id uuid REFERENCES domain_version(id)
                                   ON UPDATE CASCADE ON DELETE SET NULL,
    started_at                 timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
    start_duration             bigint,
    released_at                timestamp,
    release_duration           bigint
);
CREATE UNIQUE INDEX domain_version_unique ON domain_version(domain_id, version);
CREATE UNIQUE INDEX domain_version_one_open_per_domain ON domain_version(domain_id) WHERE status = 'OPEN';
CREATE INDEX domain_version_prev_idx ON domain_version(previous_domain_version_id);
CREATE INDEX domain_version_order_idx ON domain_version(domain_id, "order" DESC);
```

`(domain_id, version)` даёт занятость лейблов (проверяется и на UPDATE при `release_end`);
`one_open` — единственное открытое окно на домен.

### Новые колонки `domain`

```sql
ALTER TABLE domain ADD COLUMN current_domain_version_id uuid NOT NULL
    REFERENCES domain_version(id) ON UPDATE CASCADE ON DELETE RESTRICT;
ALTER TABLE domain ADD COLUMN operation_status varchar NOT NULL DEFAULT 'IDLE'
    CHECK (operation_status IN ('IDLE','IMPORTING','RELEASING','ROLLBACK'));
ALTER TABLE domain ADD COLUMN operation_started_at timestamp;   -- диагностика застреваний
ALTER TABLE domain ADD COLUMN locked boolean NOT NULL DEFAULT false;
ALTER TABLE domain ADD COLUMN locked_at timestamp;
ALTER TABLE domain ADD COLUMN locked_by uuid REFERENCES "user" ON UPDATE CASCADE ON DELETE SET NULL;
```

`current_domain_version_id` NOT NULL при циклической зависимости domain ↔ domain_version: домен
рождается before-insert-триггером, который создаёт V1 (вставка версии при ещё не вставленном
домене проходит благодаря DEFERRABLE-FK) и проставляет `NEW.current_domain_version_id`.

### Колонки каждой настроечной таблицы

```sql
ALTER TABLE <table> ADD COLUMN domain_id uuid;                    -- у корневых уже есть; NULL = системная строка
ALTER TABLE <table> ADD COLUMN domain_version_id uuid;            -- штамп; ставит только триггер
ALTER TABLE <table> ADD COLUMN row_status varchar NOT NULL DEFAULT 'ACTIVE'
    CHECK (row_status IN ('ACTIVE','DISABLED','DELETED'));
CREATE INDEX idx_<table>_domain_version ON <table>(domain_id, domain_version_id);
-- уникальные бизнес-ключи — partial: UNIQUE ... WHERE row_status <> 'DELETED'
```

### Стиль миграции колонок (по образцу TWINS-719 kk1)

Добавление служебных колонок в ~190 таблиц — helper-функция + плоский список вызовов,
в конце helper удаляется; всё идемпотентно (`IF NOT EXISTS`):

```sql
CREATE OR REPLACE FUNCTION add_domain_version_columns(tbl text) RETURNS void AS $$
BEGIN
    EXECUTE format('ALTER TABLE %I ADD COLUMN IF NOT EXISTS domain_version_id uuid', tbl);
    EXECUTE format('ALTER TABLE %I ADD COLUMN IF NOT EXISTS row_status varchar
                        NOT NULL DEFAULT ''ACTIVE''
                        CHECK (row_status IN (''ACTIVE'',''DISABLED'',''DELETED''))', tbl);
    -- domain_id — только таблицам, у которых его ещё нет (отдельный, более короткий список)
    EXECUTE format('CREATE INDEX IF NOT EXISTS %I ON %I (domain_id, domain_version_id)',
                   tbl || '_domain_version_idx', tbl);
    -- FK штампа: NOT VALID в этой миграции, VALIDATE — отдельным шагом после бэкфилла
END;
$$ LANGUAGE plpgsql;

SELECT add_domain_version_columns('twin_class');
SELECT add_domain_version_columns('twin_class_field');
-- ... полный список по разметке @DataScope

DROP FUNCTION IF EXISTS add_domain_version_columns(text);
```

Partial unique для бизнес-ключей helper не добавляет (ключи у каждой таблицы свои) — это
отдельный осознанный список в той же миграции.

Из старого драфта kk1 НЕ переносится: словарные таблицы статусов (`domain_version_status`,
`domain_operation_status` — у нас varchar + CHECK), `domain_version_ghost`, `ON DELETE SET NULL`
у FK штампа (у нас `ON DELETE RESTRICT`: сворачивание окна, на которое ещё ссылаются строки,
должно падать, а не молча отвязывать строки — это делает предусловие сворачивания
 enforce'имым самой БД), nullable `version`, PK-shift в `domain_version_get_current`
(заменён ленивым открытием окна первой правкой).

### Таблица `domain_version_audit`

```sql
CREATE TABLE domain_version_audit (
    id                      uuid PRIMARY KEY,        -- uuid_generate_v7_custom(): порядок записей
    domain_id               uuid NOT NULL REFERENCES domain ON UPDATE CASCADE ON DELETE CASCADE,
    domain_version_id       uuid NOT NULL,           -- окно-штамп; без FK — окна сворачиваются и удаляются
    table_name              varchar NOT NULL,
    row_id                  uuid NOT NULL,           -- PK изменённой строки (у всех версионируемых таблиц есть uuid id)
    operation               varchar NOT NULL,        -- INSERT / UPDATE / DELETE (soft)
    domain_operation_status varchar NOT NULL,        -- этап записи: IDLE / IMPORTING / RELEASING / ROLLBACK
    before                  jsonb,                   -- to_jsonb(OLD); NULL только для INSERT
    after                   jsonb,                   -- to_jsonb(NEW); NULL для физического DELETE
    changed_at              timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
    actor_user_id           uuid REFERENCES "user" ON UPDATE CASCADE ON DELETE SET NULL
);
CREATE INDEX domain_version_audit_window_idx ON domain_version_audit (domain_id, domain_version_id);
CREATE INDEX domain_version_audit_row_idx ON domain_version_audit (table_name, row_id);
CREATE INDEX domain_version_audit_actor_idx ON domain_version_audit (actor_user_id);
```

`domain_version_id` в аудите намеренно без FK: окна версий сворачиваются и удаляются, а история
живёт дольше версий — FK дал бы либо блокировку сворачивания (RESTRICT), либо потерю срезов
истории (SET NULL), либо удаление истории (CASCADE).

**Контракт для волн: у каждой версионируемой таблицы обязан быть суррогатный `id uuid` PK.**
Таблицам с составным бизнес-ключом (единственная в пилоте — `data_list_subset_option`) id
добавляется миграцией, составной ключ остаётся бизнес-уникальностью (partial
`WHERE row_status <> 'DELETED'`). Это убирает спец-случаи из аудита, rollback и воскрешения.
Бэкфилл таких id **детерминирован** (uuid v5 от бизнес-ключа, фиксированный namespace):
независимо мигрированные окружения сходятся к одинаковым id для одной и той же настройки —
случайный uuid разъехал бы между средами и ломал сопоставление по id при импорте.

## Черновик 1. Меняют Строку 2, добавляют Строку 4

Пользователь делает две операции:

1. **Изменяет Строку 2.** Триггер обновляет штамп — присваивает V1 (он и так V1: строка создана в этом же окне, различать не нужно).
2. **Добавляет Строку 4.** Триггер ставит штамп V1, статус ACTIVE.

`TableA` после правок:

| Строка | Содержимое | Штамп версии | Статус |
|---|---|---|---|
| Строка 1 | исходное | V1 | ACTIVE |
| Строка 2 | изменённое (правка №1) | V1 | ACTIVE |
| Строка 3 | исходное | V1 | ACTIVE |
| Строка 4 | новое | V1 | ACTIVE |

Обратите внимание: всё штамповано V1. Это нормально — первый релиз содержит всё содержимое
домена, специального случая «первый релиз без дельты» не появляется.

## Релиз 1.0

Что происходит по шагам:

1. `release_start` — домен переводится в RELEASING, правки запрещаются.
2. Java собирает артефакты: **полный снапшот** (все ACTIVE-строки домена) и **дельту** (все строки со штампом V1 — то есть четыре upsert-операции), считает хэши.
3. `release_end`: версия V1 становится RELEASED с меткой `1.0`, в неё записываются снапшот, хэш и дельта. DELETED-строк нет — чистить нечего. **Новая версия не открывается** — домен остаётся указывать на V1 (теперь RELEASED): правок нет, содержимое домена в точности равно снапшоту 1.0. Версия V2 появится только первой правкой следующего окна.

`TableA` **не меняется вообще** — штампы продолжают указывать на V1, просто V1 теперь релиз.
В этом и есть запись «строку последний раз трогал релиз 1.0».

`domain_version` после релиза:

| Версия | Статус | Метка | Снапшот / хэш / дельта | previous |
|---|---|---|---|---|
| V1 | RELEASED | 1.0 | S(1.0) / H(1.0) / Δ(1.0) | — |

(`domain.current_domain_version_id` → V1.)

---

## Черновик 2. Удаляют Строку 2, редактируют Строку 3

1. **Удаляют Строку 2.** Это первая правка после релиза 1.0 — триггер сначала **создаёт новую версию V2** (OPEN, `draft`) и переключает на неё домен, затем перехватывает удаление: строка **не удаляется физически**, вместо этого ей ставится статус DELETED и штамп V2. Строка остаётся в БД до релиза — до релиза её можно «вернуть».
2. **Редактируют Строку 3.** Окно уже открыто — штамп просто обновляется на V2, статус остаётся ACTIVE.

Обратите внимание: V2 не существовала до первой правки — версию открыла сама правка.

`TableA`:

| Строка | Содержимое | Штамп версии | Статус |
|---|---|---|---|
| Строка 1 | исходное | V1 | ACTIVE |
| Строка 2 | изменённое (правка №1) | V2 | **DELETED** |
| Строка 3 | изменённое (правка №2) | V2 | ACTIVE |
| Строка 4 | новое | V1 | ACTIVE |

## Релиз 1.1

1. Полный снапшот S(1.1) = все ACTIVE-строки: **{Строка 1, Строка 3 (после правки №2), Строка 4}**. Строки в DELETED в снапшот не входят.
2. Дельта Δ(1.1) = строки со штампом V2, разделённые по статусу:
   - **обновить/вставить:** Строка 3 (новое содержимое);
   - **удалить:** Строка 2.
3. Физическая чистка: Строка 2 окончательно удаляется из БД.
4. V2 становится RELEASED с меткой `1.1`, previous → V1. Новая версия не открывается — домен остаётся указывать на V2 (RELEASED); V3 появится первой правкой следующего окна.

`TableA` после релиза 1.1 (Строки 2 больше нет):

| Строка | Содержимое | Штамп версии | Статус |
|---|---|---|---|
| Строка 1 | исходное | V1 | ACTIVE |
| Строка 3 | изменённое (правка №2) | V2 | ACTIVE |
| Строка 4 | новое | V1 | ACTIVE |

## Черновик 3 (продолжение «и т.д.»). Отключают Строку 1, заново создают Строку 2, редактируют Строку 4

1. **Отключают Строку 1** — бизнес-операция «конфиг временно не используется». Это первая правка после релиза 1.1: создаётся V3 (OPEN), домен переключается на неё; затем статус строки → DISABLED, штамп → V3. Для приложения строка невидима, но она не удалена и попадёт в снапшот со своим статусом.
2. **Заново создают Строку 2.** Конфликта нет: старая Строка 2 была физически удалена при релизе 1.1, это обычная вставка со штампом V3. (Если бы старая ещё висела в DELETED — вставка превратилась бы в «воскрешение»: триггер нашёл бы удалённую строку с тем же ключом и обновил бы её содержимое и статус.)
3. **Редактируют Строку 4** — штамп → V3.

`TableA`:

| Строка | Содержимое | Штамп версии | Статус |
|---|---|---|---|
| Строка 1 | исходное | V3 | **DISABLED** |
| Строка 2 | новое (правка №3) | V3 | ACTIVE |
| Строка 3 | изменённое (правка №2) | V2 | ACTIVE |
| Строка 4 | изменённое (правка №4) | V3 | ACTIVE |

## Релиз 1.2

1. Снапшот S(1.2) = **{Строка 1 (DISABLED), Строка 2, Строка 3, Строка 4}** — отключённые строки ездят в снапшотах со статусом, чтобы восстановление точно воспроизводило состояние.
2. Дельта Δ(1.2) = строки со штампом V3: **обновить: Строку 1 (перевести в DISABLED), Строку 2 (вставить), Строку 4; удалить: никого.**
3. V3 → RELEASED `1.2`, previous → V2. Новая версия не открывается — домен остаётся на V3 (RELEASED); V4 появится первой правкой.

## Импорт: два режима на этом же примере

**Полный (FULL).** Цель приводится к состоянию снапшота целиком: чего нет — вставляется,
что отличается — обновляется, что лишнее — удаляется. Требований к текущему состоянию цели нет.
Так работают восстановление версии и дублирование домена. Информация об удалениях в снапшоте
не нужна — удаление выражается отсутствием строки.

**Инкрементальный (INCREMENTAL).** Применяются только дельты. Условие применимости проверяется
по текущей версии цели: `current_domain_version_id` указывает на **RELEASED**-версию (правок
после последнего релиза/импорта не было), и её хэш совпал с базовым релизом цепочки дельт.
Оба хэша хранятся на самих версиях — сравниваются два сохранённых значения, ничего не пересчитывается.

**Кейс А. Цель получила релиз 1.0 полным импортом, источник уже дошёл до 1.2.**
Текущая версия цели — импортная RELEASED-версия с хэшем H(1.0). Идём по цепочке previous от
релиза 1.2 назад: 1.2 → 1.1 → 1.0 — хэш релиза 1.0 совпал с хэшем текущей версии цели, база
найдена. Применяем по порядку: Δ(1.1) (обновить Строку 3, удалить Строку 2), затем Δ(1.2)
(обновить Строки 1, 2, 4). После импорта у цели снова RELEASED-версия — импортная, с хэшем
H(1.2). Именно так «на версию 1 сразу ставится версия 4» — промежуточные дельты включаются сами.

**Кейс Б. Цель стоит на 1.1.**
Текущая версия цели имеет хэш H(1.1), база найдена сразу — применяется только Δ(1.2).

**Кейс В. Цель на 1.0, но после импорта её конфиг кто-то правил локально.**
У цели существует OPEN-окно. INCREMENTAL-импорт начинается с отката черновика (rollback окна
по аудиту, окно сворачивается — цель возвращается на 1.0), затем применяется цепочка дельт.
Правки черновика отбрасываются — это явная часть операции (отражается в API).

**Кейс Г. Восстановление самого источника к релизу 1.0.**
Полный импорт снапшота S(1.0) в тот же домен: правки №2–№4 откатываются, строки, которых нет
в снапшоте, удаляются. Важная деталь: после любого импорта/восстановления текущей версией
становится специальная «импортная» версия (RELEASED, хэш H(1.0)), и головой цепочки для будущих
дельт будет она, а не релиз 1.2 — иначе следующая дельта считалась бы «от состояния 1.2», хотя
домен фактически вернулся к 1.0, и цель на 1.2 получила бы рассинхронизированный гибрид.

### Возврат на несколько релизов назад — обратные дельты (согласовано 2026-10-16)

FULL-restore по снапшоту универсален, но выравнивает все строки домена, даже если между
релизами изменилось пять. Для локального возврата (была 1.4, надо на 1.2) добавляем на релизную
строку пару колонок:

```sql
ALTER TABLE domain_version ADD COLUMN rollback_delta_file jsonb;   -- дельта НА предыдущий релиз
ALTER TABLE domain_version ADD COLUMN rollback_delta_hash varchar; -- SHA-256 документа дельты
```

- строится при релизе одновременно с прямой дельтой: это один и тот же diff пары снапшотов
  (S_prev, S_new) в двух направлениях; у первого релиза — NULL;
- возврат 1.4 → 1.2: (1) rollback открытого окна, если есть; (2) обратная цепочка: применить
  rollbackΔ1.4 (1.4 → 1.3), затем rollbackΔ1.3 (1.3 → 1.2); (3) импортная версия с хэшем H(1.2)
  становится текущей (механизм кейса Г — голова цепочки для будущих дельт корректна);
- возврат затрагивает только строки, изменённые между релизами; всё локально — дельты уже в БД,
  ничего не передаётся и не пересчитывается;
- путь выбирает Java: суммарный размер обратной цепочки против полного снапшота; FULL-restore —
  универсальный fallback (дальний возврат, отсутствие обратных дельт у старых релизов);
- обратные дельты — только локальный restore; импорт между средами использует прямые дельты.

## Rollback черновика (согласовано 2026-10-15)

Механизм — таблица аудита `domain_version_audit`: развитие драфта TWINS-719
(`db/migration_backlog/V1.4.xxx.xx__TWINS-719_kk2_domain_config_audit_triggers.sql`,
таблица переименована из `domain_config_audit`). Схема — в разделе «Схема (DDL)».

Отличия от драфта TWINS-719:
1. **Два образа вместо одного** (`before` + `after`) — rollback UPDATE требует старого образа, одного `snapshot` недостаточно.
2. **`domain_version_id`** — срез аудита по окну версии, без него rollback не построить.
3. **`row_id` = PK самой строки**; таблицам без uuid PK (составные ключи) id добавляется миграцией — контракт описан в разделе «Схема».
4. **Таблица резолва `domain_config_audit_resolve` не нужна** — в модели v2 каждая строка несёт `domain_id`/`domain_version_id`, аудит ничего не вычисляет по FK-цепочкам.
5. Фильтр «осмысленного изменения» общий у штампа и аудита: no-op UPDATE не пишет ни штамп, ни аудит (иначе ложные изменения в дельте). Из сравнения исключаются технические колонки, не являющиеся содержимым настройки: `updated_at`, счётчики (`twin_counter` и подобные), сам штамп `domain_version_id`. В образы `before`/`after` эти колонки входят как есть — исключение касается только детекции изменения.
6. **Аудит пишут ВСЕ пути, включая служебные** (импорт, rollback, релизная чистка) — раньше предполагалось выключать аудит под GUC; вместо этого каждая запись несёт колонку `domain_operation_status` (IDLE = обычная правка, IMPORTING, RELEASING, ROLLBACK). История полная: «строка приехала импортом 1.2», «восстановлена rollback'ом»; UI «человеческих» правок фильтрует по IDLE.

Хранение — долговременное (история «кто/когда/что»); при росте объёмов — шедулер переноса в архив (отдельная задача, не блокер).

**Алгоритм полного rollback окна:**
1. `rollback_start`: исключающий advisory-лок; статус домена → `ROLLBACK` (новое значение `operation_status`).
2. Java читает аудит окна (`domain_id` + `domain_version_id` = текущая OPEN), группирует по `(table_name, row_id)` и для каждой группы берёт **первую** запись окна (нам нужно состояние на начало окна, а не отмена последней операции):
   - `INSERT` → строка до окна не существовала → физический `DELETE` (под GUC импорта);
   - иначе → `UPDATE` всеми колонками из `before`-образа, включая **старый штамп** и старый `row_status`.
   Пустой аудит → окно пустое, no-op. Bulk-операции по таблицам, без N+1.
3. `rollback_end`: если у OPEN-версии не осталось штампованных строк — **окно сворачивается**: OPEN-версия удаляется, `current_domain_version_id` возвращается на предыдущую RELEASED-версию (домен снова «не правлен», содержимое — в точности релизный снапшот). Если строки остались (частичный rollback) — окно остаётся OPEN. Статус → IDLE. Записи аудита сохраняются (история).

**Частичный rollback** — подмножество строк окна: на шаге 2 вместо всех групп берём выбранные строки, каждая откатывается к своему состоянию на начало окна (before-образ первой записи группы строки). Семантический undo («отменить правки автора X, сохранив чужие более поздние») сознательно не делаем — для тонких случаев существует откат строки к произвольному прошлому состоянию (тип 2 ниже).

**Следствия для дельт:** восстановление старого штампа из before-образа выводит откаченные строки из следующей дельты; INSERT'ы окна при откате удаляются физически; после сворачивания пустого окна статус текущей версии снова RELEASED — домен побайтово на релизном состоянии, инкрементальные цепочки на других средах продолжают работать.

**Два типа rollback (согласовано 2026-10-15):**
1. **Rollback черновика** (описан выше — полный или по подмножеству строк): восстанавливаются
   старые штампы, откаченные строки выходят из следующей дельты.
2. **Откат строки к произвольному прошлому состоянию** — UX-операция над историей аудита:
   пользователь видит всю историю правок строки и выбирает любое прошлое состояние; система
   применяет выбранный образ как обычную правку (гейт, штамп текущей версии, аудит пишет UPDATE).
   Если выбранное состояние — начальное состояние строки в текущем окне, можно пойти путём
   типа 1 (строка выйдет из дельты); иначе — обычный апдейт, строка остаётся в дельте.
   Проблема «чужих более поздних правок» не возникает: это не отмена истории, а установка
   выбранного состояния.

## Заморозка домена — LOCK (согласовано 2026-10-15)

`operation_status` — транзитные состояния операций (после конца возвращаются в IDLE); заморозка —
персистентное состояние, поэтому живёт в отдельной колонке:

```sql
ALTER TABLE domain ADD COLUMN locked boolean NOT NULL DEFAULT false;
ALTER TABLE domain ADD COLUMN locked_at timestamp;      -- диагностика
ALTER TABLE domain ADD COLUMN locked_by uuid REFERENCES "user" ON UPDATE CASCADE ON DELETE SET NULL;
```

| Операция | Обычный домен | locked = true |
|---|---|---|
| Правки конфигурации (INSERT/UPDATE/DELETE) | да | нет |
| Релиз (открывает новую версию) | да | нет |
| Rollback черновика | да | нет |
| Импорт FULL/INCREMENTAL, restore | да | да — единственная дверь |
| Снятие LOCK | — | явная админ-операция (REST, срез B) |

Гейт правок: `operation_status = 'IDLE' AND NOT locked`. Импорт-путь проверяет только
`operation_status` — замороженный домен импорт принимает, никакого перехода LOCK↔IMPORTING.
Импорт управляет версиями сам (создаёт импортную RELEASED-версию и делает её текущей; правки всё
равно запрещены) — это задуманное исключение из «нельзя открывать новые версии». Использование:
прод-домены, конфиг меняется только контролируемым импортом из старших сред (dev → test → stage → prod).

## Защита версионных колонок (согласовано 2026-10-16)

Колонки `domain_version_id` и `row_status` принадлежат триггерам; ручные и прикладные записи
охраняются на уровне обёрток:

- **INSERT**: входящий `domain_version_id` запрещён (ошибка без служебного GUC) — штамп ставит
  before-insert обёртка (гейт → ленивое открытие окна → штамп). Входящий `row_status` допускается
  только ACTIVE/DISABLED (обычная вставка, в том числе сразу отключённой строки); DELETED ставит
  только конверсия в before-delete обёртке.
- **UPDATE**: входящее изменение `domain_version_id` → ошибка; входящая установка
  `row_status = 'DELETED'` → ошибка (удаление — только через DELETE, который конвертируется в
  soft-delete). Прямые переходы ACTIVE↔DISABLED разрешены — это бизнес-операции отключения/
  включения конфига, Java пишет их сам; обёртка перештамповывает строку и пишет аудит.
- **DELETE**: при выключенных GUC всегда конвертируется в soft-delete (`row_status = 'DELETED'`
  + штамп; в аудит пишется как операция DELETE). Физическое удаление — только служебные пути.

Служебные двери — транзакционные GUC:
- `twins.version_op` — внутренние записи наших функций и обёрток: конверсия DELETE→UPDATE,
  физическая чистка DELETED при релизе, открытие/сворачивание окна, любые записи в `domain_version`;
- `twins.import_mode` — применение внешнего содержимого с явными штампами и статусами из образов:
  импорт FULL/INCREMENTAL, restore, rollback.
- Дополнительно `pg_trigger_depth() > 1` отличает запись, сделанную из другого триггера, от
  верхнеуровневого оператора — бесплатное усиление защиты.

Таблица `domain_version`: любые записи только под `twins.version_op`; строки со статусом RELEASED
неизменяемы всегда, даже с GUC. Таблица `domain_version_audit`: INSERT только из аудита-обёрток;
UPDATE/DELETE запрещены (история неизменяема), кроме будущего архивного шедулера (под GUC).

Оговорка: GUC и `pg_trigger_depth()` защищают от случайных правок и багов, но не от DBA —
триггер можно отключить; это верно для всей механики модели.

## Краевые кейсы (согласовано 2026-10-16)

1. **Строка, рождённая и удалённая в одном окне, удаляется физически сразу.** Если первая запись
   аудита строки в окне — INSERT (до окна строка не существовала ни в одном релизе), DELETE не
   конвертируется в soft-delete, а выполняется физически; история остаётся только в аудите.
   В дельту такая строка не попадает вовсе.
2. **Воскрешение — только по PK.** Повторная вставка с тем же id находит DELETED-строку и
   превращается в UPDATE (содержимое новое, статус ACTIVE, штамп окна). Если новое содержимое
   и статус совпадают с состоянием строки на начало окна (before-образ первой записи аудита) —
   возвращается и старый штамп: строка выходит из окна и не попадает в дельту (аналог no-op).
   По не-PK уникальному ключу воскрешения нет — вставляется новая строка (partial unique index
   `WHERE row_status <> 'DELETED'`); пока жива новая строка с этим ключом, DELETED-строку
   воскресить нельзя.
3. **no-op UPDATE** — не пишет ни штамп, ни аудит (общий фильтр осмысленного изменения, см. §5
   отличий аудита).
4. **Гонки**: обычные правки — разделяемый advisory-лок до коммита; первая правка окна
   (ленивое открытие) и операции (release/import/rollback start/end) — исключающий;
   разделяемый перед исключающим не берётся (нет дедлоков). Операция стартует только после
   коммита всех начатых правок; новые правки видят статус операции и отклоняются.
5. **Rollback при LOCK** запрещён (гейт `IDLE AND NOT locked`).

### Импорт при открытом черновике — этапы с примером

Домен B: вышел релиз 1.0 {Строки 1, 2, 3, 4}, затем в окне V2 удалили Строку 2, изменили
Строку 3 и добавили Строку 5. В домен импортируется полный снапшот S\* = {Строка 1, Строка 3
(другое содержимое), Строка 7}.

Состояние до импорта:

| Строка | Содержимое | Штамп | Статус |
|---|---|---|---|
| 1 | исходное | V1 | ACTIVE |
| 2 | исходное | V2 | DELETED |
| 3 | изменённое | V2 | ACTIVE |
| 4 | исходное | V1 | ACTIVE |
| 5 | новое | V2 | ACTIVE |

**Этап 1 — rollback черновика V2 по аудиту** (как обычный rollback окна): Строка 2 — первая
запись окна DELETE → восстановить before-образ (исходное содержимое, ACTIVE, штамп V1);
Строка 3 — первая запись UPDATE → восстановить before-образ (штамп V1); Строка 5 — первая
запись INSERT → физически удалить. Окно опустело → сворачивается, `current` → V1 (RELEASED).
Домен побайтово на релизе 1.0:

| Строка | Содержимое | Штамп | Статус |
|---|---|---|---|
| 1 | исходное | V1 | ACTIVE |
| 2 | исходное | V1 | ACTIVE |
| 3 | исходное | V1 | ACTIVE |
| 4 | исходное | V1 | ACTIVE |

**Этап 2 — reconcile снапшота S\*** (не «полная чистка», а выравнивание): Строка 1 совпала —
не трогаем, штамп V1 сохраняется (провенанс); Строка 3 отличается — обновляется содержимым из
снапшота, штамп IV; Строки 7 нет — вставка, штамп IV; Строки 2 и 4 лишние — физическое
удаление (GUC импорта). Для INCREMENTAL вместо reconcile применяется цепочка дельт
(delete-опы + upsert-опы).

**Этап 3** — импортная версия IV (RELEASED, хэш снапшота/дельты), все применённые строки
штампованы IV, `current_domain_version_id` → IV. Итог:

| Строка | Содержимое | Штамп | Статус |
|---|---|---|---|
| 1 | исходное | V1 | ACTIVE |
| 3 | из снапшота | IV | ACTIVE |
| 7 | из снапшота | IV | ACTIVE |

### Механика FULL-reconcile (согласовано 2026-10-16)

Поиск лишних/изменившихся/недостающих — **generic-запросами БД** по temp-таблице снапшота,
применение найденного — **Java-батчами** (мапперы уже есть). Ни чтения всех строк в память,
ни перезаписи неизменившихся, ни второй копии маппинга колонок:

```sql
-- Java один раз грузит снапшот:
CREATE TEMP TABLE import_payload (table_name text, row_id uuid, data jsonb);

-- лишние: anti-join, одна инструкция на таблицу
DELETE FROM <table>
 WHERE domain_id = :D
   AND id NOT IN (SELECT row_id FROM import_payload WHERE table_name = '<table>');

-- изменившиеся: сравнение jsonb-образа строки с payload (без per-table маппинга)
SELECT r.id
  FROM <table> r
  JOIN import_payload p ON p.table_name = '<table>' AND p.row_id = r.id
 WHERE (to_jsonb(r) - 'updated_at' - 'domain_version_id') IS DISTINCT FROM p.data;

-- недостающие: id из payload, которых нет в таблице; вставка и обновление — Java-батчами
```

Ключ сопоставления — `id` строки. Неизменившиеся строки не трогаются и сохраняют штампы
(провенанс). Порядок: вставки в порядке FK-зависимостей (родители раньше детей), удаления —
в обратном; всё в одной транзакции импорта под GUC `twins.import_mode`; системные строки
(`domain_id IS NULL`) вне среза `domain_id = :D` — не затрагиваются никогда.

Почему не «перезапись всего с новой цепью»: стирается провенанс (все штампы → IV), рвётся
цепочка `previous` (обратные дельты локальной истории), write-all вместо write-diff. Почему не
штамповый критерий «родности» (строки со штампами вне цепи): «лишняя» строка может быть «родной»
(штамп в цепи, а в снапшоте её нет) — lineage отвечает «откуда строка», а не «есть ли она в
снапшоте». Колонка `order` и функция чистки сирот при этом полезны сами по себе:

- **`domain_version.order`** — монотонный счётчик домена (присваивается при релизе/импорте):
  сортировка версий и walk цепочки; в критерии родства не используется.
- **`domain_version_reconcile(domain_id)`** — DB-функция чистки «сирот»: строки со штампами
  вне цепи текущей версии (осиротели после багов/ручных правок в обход триггеров). Режимы
  репорт/удаление; инвариант-чекер по расписанию и после сбоев. Это НЕ механизм
  reconcile-с-снапшотом — только гигиена.

## Согласовано дополнительно (2026-10-15/16)

- **id версий — uuid v7** (`uuid_generate_v7_custom()`); детерминизм отменён — занятость лейбла
  ловит уникальный индекс `(domain_id, version)` (PostgreSQL проверяет его и на UPDATE при `release_end`).
- **Первая дельта = полный состав**: единое правило «дельта релиза = строки со штампом релизящейся
  версии»; инкрементальный импорт в пустую цель = применение первой дельты, FULL не обязателен.
- **Снапшот содержит статусы строк**: DISABLED едет в FULL/restore (иначе restore молча включит
  отключённый конфиг); DELETED в снапшот не входят — удаление выражается отсутствием строки.
- **DISABLED — в скоупе модели** (вытекает из решения о снапшотах).
- **Механика удалений — tri-state `row_status`** (исходный вариант модели): soft-delete до релиза,
  конверсия DELETE→UPDATE в before-триггере, «воскрешение» при повторной вставке того же
  бизнес-ключа, partial unique индексы для бизнес-ключей (`WHERE row_status <> 'DELETED'`).
- **Ленивое открытие версий**: релиз НЕ открывает следующую версию — её создаёт первая правка.
  Путь открытия берёт исключающий advisory-лок, прочие правки — разделяемый (разделяемый лок
  перед исключающим не берём — дедлоков нет). Статус текущей версии заменяет флаг
  «правили/не правили», отдельная маркер-колонка не нужна. Проверка базы при INCREMENTAL:
  текущая версия цели RELEASED и её хэш совпал с базовым релизом цепочки дельт.
  Исключение — рождение домена: `current_domain_version_id` NOT NULL, триггер after-insert на
  `domain` сразу создаёт V1 (OPEN). После релиза новое окно открывается только правкой. Окно
  может опустеть, если все его правки отменены (воскрешение без изменений, откат строк): такое
  окно сворачивается rollback'ом/импортом либо релизится с пустой дельтой (безвредно). Самый
  первый бейзлайн-релиз пустого домена возможен и безвреден.
- **Дельта строится по итоговому состоянию окна, а не по журналу операций**: на релизе каждая
  строка со штампом релизящейся версии даёт ровно одну операцию — upsert, если строка жива
  (ACTIVE/DISABLED), delete, если осталась DELETED. Порядок применения внутри дельты не важен;
  delete-опы толерантны к отсутствию строки на цели (защита от рассинхронов). Строки, рождённые
  и удалённые в одном окне, в дельту не попадают вообще (см. краевые кейсы).
- **Импорт при открытом окне — сначала rollback черновика**: окно откатывается по аудиту и
  сворачивается (пустое окно нового домена — просто сворачивается), затем применяются дельты
  (INCREMENTAL) или reconcile снапшота (FULL), изменённые/вставленные строки штампуются
  импортной версией, `current_domain_version_id` → импортная RELEASED-версия.
- **Rollback сворачивает пустое окно**: если после отката у OPEN-версии не осталось нетто-изменений
  — версия удаляется, `current_domain_version_id` возвращается на RELEASED-версию. Нетто-проверка —
  одним запросом по журналу аудита (группа строки = нетто-ноль, если её последняя запись в срезе
  окна — физический DELETE): бэкфилл заполняет аудит синтетическими INSERT-записями базовой линии,
  «рождено+удалено в одном окне» и воскрешение-без-изменений (дописывает закрывающий DELETE-маркер
  в срез окна) дают нетто-ноль без опроса таблиц.
- **`domain_version.order`** — монотонный счётчик домена (при релизе/импорте): сортировка и walk
  цепочки; в критериях родства не используется.
- **`domain_version_reconcile(domain_id)`** — DB-функция чистки «сирот» (строки со штампами вне
  цепи текущей версии), режимы репорт/удаление; гигиена, не механизм импорта.
- **FULL-reconcile — гибрид БД+Java**: temp-таблица снапшота, лишние/изменившиеся ищет БД
  generic-запросами (anti-join + jsonb-сравнение), применяет Java батчами (см. Краевые кейсы).
- **Аудит пишут все пути** с тегом этапа `domain_operation_status` (IDLE/IMPORTING/RELEASING/
  ROLLBACK) — история полная, «человеческие» правки фильтруются по IDLE.
